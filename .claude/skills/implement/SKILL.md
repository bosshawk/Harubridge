# 実装の統括

あなた（このスキルを読んでいるエージェント）は**統括者**である。
**自分ではコードを書かない。** 実装もレビューも修正も、
`.claude/agents/` のサブエージェントに委ねる。あなたの仕事は次の 4 つに限る。

1. 前提を確認し、タスクを分割する
2. サブエージェントに**十分な文脈を渡して**起動する
3. 報告と指摘を仕分けし、次のサブエージェントに回す
4. 人間にしか決められない論点で止め、完了条件を検証して報告する

サブエージェントは会話の文脈を見られない。
**依頼文には毎回、参照すべき文書・対象範囲・完了条件を明記する**（CONTRIBUTING.md の依頼の書き方）。

## 手順 0: 前提の確認（実装を始めてよいか）

- [ ] 該当機能の外部仕様（`docs/spec/external/`）が存在するか。
      **無いなら実装を始めない。** `capture-issue` スキルで論点を整理し、人間の判断を待つ
      （docs-first。CLAUDE.md §0）
- [ ] `docs/spec/constraints.md` に反していないか（特に C-01 / C-02）。
      反するなら実装せず、その旨を報告して終了する
- [ ] 艦これ側の仕様への依存があるか。あるのに `docs/kancolle/` に記録が無ければ、
      先に `kancolle-researcher` で調査する（推測で実装しない）。
      軽い確認だけなら `kancolle-expert` に質問する
- [ ] 作業ツリーが汚れていないか（`git status`）。汚れていたら人間に確認する

## 手順 1: 分割と計画

- [ ] タスクを **Rust 側**（`crates/` / `src-tauri/`）と
      **フロントエンド側**（`src/` / `src-tauri/injected/`）に分ける
- [ ] 依存の向きを決める。**型が Rust → `bindings.ts` → UI と流れるため、
      境界の型に触れる変更は Rust 側が先。** 独立していれば並行してよい
- [ ] 各担当への依頼文を組み立てる。必ず含めるもの:
  - 実装する外部仕様の該当箇所（ファイルと E-xx / FR の ID）
  - 対象範囲（触ってよいファイル・触ってはいけないファイル）
  - 完了条件（どの検査が通れば終わりか）
  - 関連する `docs/kancolle/` の記録（API 構造・計算式に触れる場合）

## 手順 2: 実装（サブエージェント）

- [ ] Rust 側は `rust-implementer`、フロントエンド側は `frontend-implementer` を起動する
- [ ] 報告を読み、次を確認する:
  - 検査が通ったと**コマンドと結果付きで**報告されているか。
    通っていない実装を「できた」と扱わない
  - **実装を止めて報告してきた事項**（glossary に無い訳語・仕様の不足・依存の追加）が
    ないか。あれば実装を先に進めず、手順 5 の「人間に返す論点」へ回す
- [ ] 実装が外部仕様の範囲を超えていないか、diff をあなた自身が読んで確かめる
      （仕様に無い振る舞いは削らせる。C-06）

## 手順 3: レビューと修正のサイクル（最大 3 回）

1 サイクル = **レビュー → 仕分け → 修正**。これを最大 3 回繰り返す。

### レビュー

- [ ] 変更が触れたスタックのレビューアを起動する
      （Rust → `rust-reviewer`、TypeScript / 注入スクリプト → `typescript-reviewer`。
      両方に触れたなら**両方を並行に**）
- [ ] 依頼文にレビュー対象の範囲（diff の取り方）と、実装した E-xx の ID を書く

### 仕分け（あなたの仕事。ここはサブエージェントに委ねない）

指摘を次の 3 つに分ける。

| 分類 | 扱い |
| --- | --- |
| **修正する** — ルール ID のある違反、外部仕様との不一致 | 修正依頼へ |
| **見送る** — レビューアの誤検出・ルールに無い好み | 理由を記録する。**黙って捨てない** |
| **人間に返す** — 仕様・ガイドライン側を変えるべき根拠、判断の分かれる設計論点 | 手順 5 へ。**このサイクルでは修正しない** |

誤検出かどうかはガイドライン本文（`docs/guidelines/`）に当たって判定する。
判定に迷うものは「人間に返す」に入れる。

### 修正

- [ ] 「修正する」に分類した指摘を、**該当スタックの implementer に差し戻す。**
      依頼文にはレビューアの指摘を**ルール ID・ファイル・行ごと転記**する
      （サブエージェントはレビュー報告を見られない）
- [ ] 修正報告を受けたら次のサイクルへ

### 終了条件

- **MUST 違反（深刻度 a / b）の指摘がゼロのサイクルがあれば、そこで打ち切ってよい**
- **3 サイクル終えても MUST 違反が残っているなら、それ以上繰り返さない。**
  残った指摘を付けて人間に報告する（同じ指摘が 2 サイクル続いたら、
  それは実装の問題ではなく設計か仕様の問題である）

## 手順 4: 最終検査

- [ ] `task check` をあなた自身が実行し、全検査が通ることを確かめる
      （サブエージェントの報告を信用して省略しない）
- [ ] CLAUDE.md §5 の完了条件を照合する:
  - 外部仕様と実装が一致している
  - 基本設計に影響したなら `docs/spec/architecture.md` の更新**案**がある（変更は承認後）
  - 新たな設計判断は ADR の起票が要るか判定した（要るなら `write-adr`）
  - 未解決事項が仕様書の「未解決事項」節に必要か判定した

## 手順 5: 報告

人間への報告に必ず含めるもの。

1. 実装した外部仕様の ID と、変更したファイルの一覧
2. サイクルごとの要約（指摘数と内訳: 修正 / 見送り / 人間行き）
3. **見送った指摘とその理由**（レビューアの誤検出を含む）
4. **人間に返す論点**（仕様・ガイドライン・glossary の変更が要るもの、依存の追加、
   判断の分かれる設計論点）。それぞれ現状・問題・選択肢を付ける
5. 最終検査（`task check`）の結果
6. 3 サイクルで解消しなかった指摘（あれば）

コミットはこの報告の後。**人間の指示を受けてから** `commit` スキルで行い、
仕様変更と実装を同じコミットに混ぜない（CLAUDE.md §4）。

## 統括者が守ること

- **自分でコードを書かない・直さない。** 1 行の修正でも implementer に委ねる。
  例外は仕分けの判定に使う読み取りだけ
- **レビューアに修正させない・implementer にレビューさせない。** 役割を混ぜると
  「書いた本人が自分を審査する」状態に戻る
- サイクルの途中でスコープを広げない。実装中に見つけた別の問題は
  修正させず、報告の「人間に返す論点」か `capture-issue` に積む
- `docs/spec/` と `docs/guidelines/` を変更しない（承認が要る領域。案の提示まで）
