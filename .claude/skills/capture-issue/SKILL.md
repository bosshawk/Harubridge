# 論点を Issue に残す・閉じる

**他人（将来の自分を含む）が読む必要がある**論点・検討・調査ログは **GitHub Issue** に置く
（[ADR-0015](../../../docs/adr/0015-documentation-layout.md)）。

書き捨ての作業メモは `docs/notes/` に置いてよい。ここは **git 管理対象外で共有されない**
（[ADR-0015](../../../docs/adr/0015-documentation-layout.md)）。
**それ以外の場所にリポジトリ内メモを作らない。**

| 判断 | 置き場所 |
| --- | --- |
| 他人が読む必要がある | GitHub Issue |
| 読む必要が無い・書き捨て | `docs/notes/`（共有されない） |

迷ったら Issue に立てる。`docs/notes/` に書いたものは失われたのと同じになる。

## A. Issue を立てる

### 1. 既存を確認する

```bash
gh issue list --state all --search "<キーワード>"
```

同じ論点の Issue があれば、新規作成せずコメントを追加する。

### 2. 立てる

```bash
gh issue create --title "<論点を一言で>" --label "<種類>" --body "$(cat <<'EOF'
## 何を決めたいか

（1 〜 3 文。決めるべき問いを明確に）

## 分かっていること

- 事実には出典（URL + 参照日）を書く

## 分からないこと

- `TODO(要確認)`: 人間の判断が必要なもの

## 選択肢

### 案 A
- 利点 / 欠点

### 案 B
- 利点 / 欠点

## 現時点の見立て

（推奨案を挙げてよいが、**決定はしない**）
EOF
)"
```

ラベルの目安: `question`（人間の判断待ち）/ `research`（調査）/ `decision`（決定待ち）。

### 3. 守ること

- **1 Issue 1 論点。** 長くなったら分ける。
- **事実と推測を分ける。** 出典が無い記述には `TODO(要検証)` を付ける。
- **意思決定はしない。** 選択肢とトレードオフを並べるところまでが仕事。
  決めるのは人間（[CONTRIBUTING.md](../../../CONTRIBUTING.md)）。
- 艦これの API 仕様は非公開。推測を事実として書かない
  （[constraints.md](../../../docs/spec/constraints.md) C-03）。
- **公開リポジトリである。** 提督名・認証情報・通信ログを Issue に貼らない（C-07）。

## B. Issue を閉じる

決着したら必ず閉じる。**放置しない。**

| 決着の内容 | すること | 使うスキル |
| --- | --- | --- |
| 案を比較して 1 つ選んだ | ADR を起票 | `write-adr` |
| ユーザーへの約束が決まった | `docs/spec/external/` を更新 | `write-spec` |
| 機能をまたぐ構造が決まった | `docs/spec/architecture.md` を更新 | `write-spec` |
| 横断ルールが決まった | `docs/guidelines/` を更新 | `write-spec` |
| 実装の詳細が決まっただけ | **何も文書化しない**（コードが正） | — |
| 不要になった | そのまま閉じる | — |

```bash
gh issue close <番号> --comment "ADR-000X で決着: <リンク>"
```

**Issue の本文を仕様書に転記しない。** 決定は ADR へ、現在の姿は仕様へ、
検討の経緯は Issue に残したまま閉じる。

## 判断に迷ったら

「これは Issue か、仕様か」で迷ったら **Issue に書く。**
Issue から仕様への昇格は安全だが、未確定の記述が仕様にあると
エージェントがそれを確定仕様として実装してしまう。
