# データ検証

`data/` は**アプリが実行時に使う正のデータ**である（[data/README.md](../../../data/README.md)）。
手で書くデータには必ず誤りが混入する。この手順はそれを機械的に検出する。

## 前提

- [data/README.md](../../../data/README.md) — データの書き方の規律
- [docs/spec/constraints.md](../../../docs/spec/constraints.md) — 特に C-03（出典必須）と C-05（アセット同梱禁止）
- [docs/kancolle/sources.md](../../../docs/kancolle/sources.md) — 出典として許される情報源とライセンス
- [docs/spec/architecture.md](../../../docs/spec/architecture.md) の「外部データの取り込み」

## 手順

### 1. 形式の検査

- [ ] JSON としてパースできるか（`jq . data/kancolle/*.json`）
- [ ] **各レコードに `source`（出典）と `verified`（確認日）があるか。** 無いレコードは列挙する
- [ ] 未確認の値が `null` または `TODO(要検証)` になっているか。
      **もっともらしい数値で埋まっている場所こそ疑う**（推測で埋めない規律）

### 2. 出典の検査

- [ ] `source` が [sources.md](../../../docs/kancolle/sources.md) で**参照可**とされた情報源か。
      ライセンス無し（`kcwikizh/kcdata` / `noro6/kc-web` のソースなど）を出典にしたレコードは**違反**
- [ ] `verified` の日付が妥当か（未来日・極端に古い日付は疑う）
- [ ] 出典側が「推測を含む」と断っている値に、その但し書きが引き継がれているか

### 3. docs との整合

- [ ] `data/` の値に対応する説明が `docs/kancolle/` にあるか（値は data、説明は docs）
- [ ] **同じ値が docs 側にも書かれていないか。** 値の二重管理は違反。docs 側は説明とリンクに直す
- [ ] docs 側の記述と data 側の値が食い違っていないか。食い違いは**どちらが正か判断せず両方を報告**する

### 4. 内容の抜き取り検証

全件は不要。**次の優先順で抜き取り、出典に当たって値を照合する。**

1. `verified` が最も古いレコード
2. 直近の変更で追加・更新されたレコード
3. ゲーム更新（イベント・新任務）の影響を受けそうな領域

照合には [sources.md](../../../docs/kancolle/sources.md) の「調べる順序」に従う。
**独立した 2 つ以上の情報源で確認できたものだけ「照合済み」と報告する。**

### 5. ビルド時検証

- [ ] `cargo test -p harubridge-core -p repo-guard` が通るか
- [ ] `build.rs` の検証がこのデータの不変条件（ID の一意性・参照整合など）を実際に検査しているか。
      **データに新しい種類の誤りを見つけたら、ビルド時検証への追加を提案する**
      （実行時ではなくビルド時に検出する。[architecture.md](../../../docs/spec/architecture.md)）

## 報告に必ず含めるもの

1. 検査したファイルとレコード数
2. 違反の一覧（出典欠落 / 参照不可の出典 / 推測埋め / docs との食い違い / 二重管理）
3. 抜き取り照合の対象と結果（一致 / 不一致 / 出典に到達できず）
4. `TODO(要検証)` の残数
5. ビルド時検証への追加提案（あれば）

**修正してよいのは、出典を確認できた明白な誤りだけ。**
判断が要る食い違いは修正せず報告する。
