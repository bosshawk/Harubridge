# ADR を書く

## 使う場面

- あとから変えるのが高くつく判断をした（技術構成 / 外部依存 / データの持ち方 / 配布方法）
- 複数の案から 1 つを選んだ
- 既存の決定を覆す必要が出た
- 法的・規約的なリスクに関わる方針を定めた

**使わない場面**: 局所的で簡単に戻せる判断。コード内コメントか spec で足りる。

## 手順

### 1. 既存 ADR を確認する

`docs/adr/README.md` の一覧を読む。

- 同じ論点の ADR が既にある → 新規作成ではなく、その ADR を Supersede する形にする
- 既に却下された案を再提案していないか確認する

### 2. 番号を決める

`docs/adr/` の最大番号 + 1。**欠番を作らない。**
ファイル名は `NNNN-english-kebab-title.md`（4 桁ゼロ埋め、英小文字ケバブ）。

### 3. テンプレートから書く

`docs/adr/template.md` をコピーする。書くときの注意:

- **「決定」節は断定形で 1〜3 文。** 読み手が最初に結論を得られること。
- **却下した案を必ず書く。** 却下理由が本体である。「なんとなく」は禁止。
  却下案が書けないなら、それは検討していないということ。
- **「決め手」でトレードオフを明示する。** 何を取って何を捨てたのか。
- 根拠が推測の場合は `TODO(要検証)` を付ける
  （艦これの API 仕様は非公開。[constraints.md](../../../docs/spec/constraints.md) C-03）。
- ステータスは **`Proposed` で作る。** 人間の承認を得るまで `Accepted` にしない。

### 4. 一覧を更新する

`docs/adr/README.md` の表に 1 行追加する。**忘れやすい。**

### 5. 関連文書を更新する

- 決定が仕様に影響する → `docs/spec/` の該当ファイルを更新する
- 元になった暫定メモがある → `docs/notes/` の該当メモを `昇格済み` にし、
  昇格先リンクを書いて `docs/notes/archive/` へ移動する

### 6. コミットする

```
docs(adr): ADR-NNNN <日本語の要約>
```

## 既存の決定を覆すとき

**旧 ADR の本文を書き換えてはいけない。**

1. 新しい ADR を起票する（「背景と課題」に、なぜ ADR-XXXX を覆すのか書く）
2. 旧 ADR の**ステータス行だけ**を `Superseded by ADR-NNNN` に変更する
3. 旧 ADR の他の記述には触れない

## チェックリスト

- [ ] 番号が連番で、欠番が無い
- [ ] 却下した案とその理由が書かれている
- [ ] 「決定」が断定形で書かれている
- [ ] ステータスが `Proposed`（人間の承認前）
- [ ] `docs/adr/README.md` の一覧を更新した
- [ ] 関連する spec / notes を更新した
