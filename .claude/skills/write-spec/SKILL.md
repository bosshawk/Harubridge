# 仕様書を書く

`docs/spec/` は**いまの正解**だけが書かれている状態を保つ場所。
経緯や却下案は書かない（それは [ADR](../../../docs/adr/) の仕事）。

## 手順

### 1. 影響範囲を確認する

- [`docs/spec/constraints.md`](../../../docs/spec/constraints.md) を読む。制約に反する仕様を書かない。
- 関連する ADR を読む。既に否決された方針を書かない。
- 既に同じことが別ファイルに書かれていないか確認する。**同じ事実を 2 箇所に書かない。**

### 2. 書く場所を選ぶ

| 内容 | ファイル | 変更に承認が要るか |
| --- | --- | --- |
| プロダクト全体の方向性・スコープ | `overview.md` | 要る |
| 越えてはならない制約 | `constraints.md` | 要る |
| 要求の追加・変更 | `requirements.md` | 要る |
| ユーザーから見える振る舞い | `external/<機能名>.md` | **要る** |
| 実現方法・構造 | `internal/<機能名>.md` | 要らない（外部仕様を変えない限り） |
| 機能に属さない横断ルール | `guidelines/<名前>.md` | 要る |
| 新しい用語 | `glossary.md` | 要らない |

承認境界の根拠は [ADR-0006](../../../docs/adr/0006-split-external-and-internal-spec.md)。
**承認が要る文書を、確認なしに書き換えてはいけない。** 変更案を提示して判断を仰ぐ。

#### 外部仕様と内部仕様の切り分け

**判断基準は再掲しない。**
[docs/spec/README.md](../../../docs/spec/README.md#外部仕様と内部仕様の切り分け) を
**必ず読んでから**分類すること（[ADR-0007](../../../docs/adr/0007-observability-based-spec-boundary.md)）。

そこに書かれた境界例（実行形態 / 保存場所と保存形式 / 性能の目標値と手段）は
直感に反するため、記憶に頼らず毎回参照する。

`internal/` のファイルは必須ではない。作成条件も同じ文書の「ファイルの粒度」に従う。
**同じ事実を両方に書かない。** 異常時の挙動は外部仕様の `E-nn` を正とし、内部仕様は ID で参照する。

### 3. 書く

**時制は現在形。** 「〜する」「〜である」。
「〜する予定」「〜だった」「〜に変更した」は書かない。

- 要求には ID を振る（`FR-nnn` / `NFR-nnn`）。**一度振った ID は再利用しない**
  （削除した要求の ID は欠番のまま残す）。
- 実装が「この記述に一致していれば正しい」と言える粒度まで書く。
  曖昧な形容詞（「使いやすい」「高速な」）は数値か具体的な挙動に置き換える。
- **未確定を隠さない。** `TODO(未確定): …` と明記する。空欄・省略は禁止。
- **出典の無い事実を書かない。** 艦これの API 構造は非公開のため、
  実測日や参照 OSS を根拠として併記する。根拠が無ければ `TODO(要検証)`。
- 異常系を必ず書く。特に「未知のデータが来たときどうするか」（NFR-003 の縮退動作）。

### 4. 整合を取る

- 新しい用語を使った → `glossary.md` に追加
- 仕様の背景に設計判断がある → ADR があるか確認。無ければ `write-adr` で起票
- 元になった暫定メモがある → `docs/notes/` のメモを昇格させて archive へ
- 要求を追加した → `requirements.md` の表と、詳細仕様ファイルを相互リンク
- 仕様ファイルを作った → 該当ディレクトリの README の一覧表に 1 行追加

> **相互リンクの追記と一覧表の更新に承認は不要。** 承認が必要な文書が対象でも、
> 内容を変えない機械的な同期作業として扱う。ここで作業を止めないこと。

### 5. コミットする

```
docs(spec): <日本語の要約>
```

仕様の変更と実装は**別コミット**にする。順序は仕様が先。

## やってはいけないこと

- 経緯・議論・却下案を書く（→ ADR / notes へ）
- 「検討中」「〜かもしれない」を確定仕様の文体で書く（→ notes へ）
- 推測した API 構造を根拠なしに書く（実装が誤りを確信して作られる）
- 未確定部分を黙って空欄にする

## チェックリスト

- [ ] 承認が必要な文書を、無断で書き換えていない
- [ ] 外部仕様と内部仕様が正しく切り分けられ、相互リンクされている
- [ ] 現在形で書かれている
- [ ] 制約（constraints.md）に反していない
- [ ] 要求 ID が重複・再利用されていない
- [ ] 未確定箇所に `TODO(未確定)` / `TODO(要検証)` が付いている
- [ ] 異常系・縮退動作が書かれている
- [ ] 新しい用語を glossary.md に追加した
- [ ] 同じ事実を 2 箇所に書いていない
