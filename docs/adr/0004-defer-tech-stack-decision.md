# ADR-0004: 技術構成の決定を要求定義のあとに延期する

- ステータス: Superseded by [ADR-0016](0016-tech-stack.md)（技術構成の決定により保留を解除）
- 日付: 2026-08-01
- 決定者: プロジェクトオーナー
- 関連: [docs/notes/2026-08-01-tech-stack-open-questions.md](../notes/2026-08-01-tech-stack-open-questions.md), [docs/spec/constraints.md](../spec/constraints.md)

## 背景と課題

艦これ専ブラの実装形態には、デスクトップアプリ / ブラウザ拡張 / ローカルサーバ + ブラウザなど
複数の方向性がある。それぞれ実現できる機能とリスクが大きく異なるため、
先に技術を選ぶと、**選んだ技術で作れる範囲に要求が引きずられる**。

一方で「何も決めない」と、エージェントが実装を始める際に既定路線を勝手に仮定する恐れがある。

## 決定

技術構成（言語 / フレームワーク / 実行形態 / 配布方法）の決定を、
[`docs/spec/requirements.md`](../spec/requirements.md) の要求が
オーナーによって承認されるまで**明示的に保留**する。

保留期間中は以下を守る。

- 技術構成に関する検討は `docs/notes/` にのみ記録し、spec には書かない。
- エージェントは特定の技術を前提とした実装・スキャフォールドを作らない。
- 技術構成が決まった時点で、本 ADR を `Superseded by` する新規 ADR を起票する。

## 検討した選択肢

### 案 A: 要求定義を先に固めてから技術選定する（採用）

- 利点: 要求が技術に引きずられない。捨てる選択肢の理由が明確に書ける。
- 欠点: 実装開始までの時間が延びる。

### 案 B: 先に技術構成を決めて、動くものを早く作る

- 利点: 早期にフィードバックが得られる。エージェントが即座に着手できる。
- 欠点: 通信の取得方法（後述の論点）次第で実装形態が根本から変わるため、
  作り直しのコストが大きい。
- 却下理由: 本プロジェクトでは「何を取得できるか」が実装形態を規定する構造になっており、
  要求より先に技術を決めると手戻りが確実に発生するため。

### 案 C: 複数構成のプロトタイプを並行して作る

- 利点: 実測に基づいて選べる。
- 却下理由: 要求が未確定のうちは評価軸が定まらず、比較にならない。
  要求承認後に、必要なら検証（スパイク）として実施する。

## 決め手

このプロジェクトの技術選定は、**制約（[constraints.md](../spec/constraints.md)）と
要求から導かれる従属変数**であり、独立に決められるものではないと判断した。

## 影響

- 実装への影響: 実装は要求承認まで開始しない。
- ドキュメントへの影響: 技術に関する検討は notes に隔離される。
- 取り消す場合のコスト: 低。要求承認を待たずに選定を始めることはいつでも可能。
