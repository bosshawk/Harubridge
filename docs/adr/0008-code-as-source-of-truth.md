# ADR-0008: 詳細仕様はコードを正とし、文書は基本設計とガイドラインに絞る

- ステータス: Accepted
- 日付: 2026-08-02
- 決定者: プロジェクトオーナー
- 関連: [ADR-0003](0003-agent-driven-development.md), [ADR-0006](archive/0006-split-external-and-internal-spec.md)（本 ADR が `internal/` に関する決定を置き換える）, [ADR-0007](archive/0007-observability-based-spec-boundary.md)

## 背景と課題

[ADR-0006](archive/0006-split-external-and-internal-spec.md) で `docs/spec/` を
external / internal / guidelines に分割したが、`internal/` のテンプレートには
モジュール構成・データモデル・処理フロー・テスト方針といった節が並んでいた。

これらは**すべてコードを読めば分かる**。文書化すると、以下が起きる。

- 実装が変わるたびに二重更新が必要になり、必ず片方が古くなる
- 古い内部仕様は、エージェントにとって**誤った前提**として作用する
  （[ADR-0003](0003-agent-driven-development.md) の体制では、文書が入力そのものであるため害が大きい）
- 更新コストを嫌って文書が放置され、「あるのに信用できない文書」が生まれる

一方で、コードを読んでも分からないものは確かに存在する。
**全体の骨格（なぜこの構造なのか）と、守るべき規約**である。これらは失われると復元できない。

## 決定

**文書として維持するのは、コードから読み取れないものだけに絞る。**

| 対象 | 置き場所 | 扱い |
| --- | --- | --- |
| 意思決定と却下案 | `docs/adr/` | 永続・不変 |
| **基本設計**（全体構造・データの持ち方の原則・境界） | `docs/spec/architecture.md` | **維持・メンテする** |
| **ガイドライン**（規約・エラー処理方針・テスト方針） | `docs/spec/guidelines/` | **維持・メンテする** |
| 外部仕様（ユーザーへの約束と受け入れ条件） | `docs/spec/external/` | 最小限に保つ |
| 機能ごとの内部仕様・処理フロー・データ構造 | **コード** | 文書化しない |

具体的な変更:

1. **`docs/spec/internal/` を廃止する。** 機能ごとの内部仕様は書かない。
   コードが正である。
2. 代わりに **`docs/spec/architecture.md`（基本設計）** を置く。
   ここには「機能をまたいで効く構造」だけを書き、個別機能の実装詳細は書かない。
3. `docs/spec/external/` は**ユーザーへの約束と受け入れ条件に絞る**。
   画面の内部構造や実現方法を書かない。
4. コードを読んでも分からない**設計意図は ADR に書く**。
   基本設計は「いまの構造」を、ADR は「なぜその構造か」を担当する。

[ADR-0007](archive/0007-observability-based-spec-boundary.md) の切り分け基準は引き続き有効。
「ユーザーが違いに気づくなら外部仕様」であり、気づかないものは
**コード（骨格に関わるものだけ基本設計）** が受け持つ、と読み替える。

## 検討した選択肢

### 案 A: 内部仕様を廃止し、基本設計とガイドラインのみ維持する（採用）

- 概要: 上記のとおり。
- 利点: 二重管理が消える。残る文書は更新頻度が低く、実際にメンテできる。
  「文書は信用してよい」という状態を保てる。
- 欠点: コードを読まないと分からないことが増える。
  エージェントは実装前に関連コードを読む必要がある。

### 案 B: 内部仕様を維持し、実装と同時更新を義務づける

- 概要: 完了条件に「内部仕様の更新」を含める。
- 却下理由: 義務づけは守られない前提で設計すべきである
  （[ADR-0002](archive/0002-documentation-structure.md) と同じ思想）。
  更新漏れが 1 度でも起きれば、以後その文書は信用できなくなる。

### 案 C: 内部仕様をコードから自動生成する

- 概要: docstring などから生成する。
- 却下理由: 生成できるのはコードに書いてあることだけであり、
  「読めば分かること」を別の形で並べ直すに過ぎない。
  失われて困る情報（なぜこの構造か）は生成できない。

## 決め手

**網羅性を捨てて、信用できる文書だけを残した。**
古い内部仕様は「無い」より悪い。エージェントはそれを正しい前提として実装するため。

## 影響

- ドキュメントへの影響:
  - `docs/spec/internal/` を削除し、`docs/spec/architecture.md` を新設する。
  - `docs/spec/external/_template.md` から実現方法に関する節を削る。
  - `docs/README.md` / `docs/spec/README.md` / `CLAUDE.md` / `write-spec` スキルを更新する。
- 実装への影響:
  - **実装前に関連コードを読むことが必須になる。**
    「仕様書に書いていないから存在しない」は内部構造には適用しない。
  - 完了条件から「内部仕様の更新」が外れ、代わりに
    「基本設計に影響する変更なら `architecture.md` を更新」が入る。
- [ADR-0003](0003-agent-driven-development.md) の docs-first は、
  **外部から見える振る舞い**に対してのみ適用される、と範囲が狭まる。
- 取り消す場合のコスト: 低（仕様ファイルはまだ 1 つも書かれていない）。
