# ADR-0022: 生の観測データを既定で保存せず、テストフィクスチャは生成器の出力に限る

- ステータス: Proposed
- 日付: 2026-08-02
- 決定者: 承認待ち（`Accepted` にする時点で承認者名に書き換える）
- 関連: [ADR-0005](0005-publish-as-oss.md), [ADR-0016](0016-tech-stack.md), [ADR-0018](0018-dependencies.md),
  [docs/spec/constraints.md](../spec/constraints.md)（C-03 / C-04 / C-07）,
  [docs/spec/requirements.md](../spec/requirements.md)（NFR-003 / NFR-004 / NFR-005 / NFR-008）,
  [docs/spec/architecture.md](../spec/architecture.md)

## 背景と課題

同じ根を持つ 2 つの問題が、実装に入る前に決まっていない。

**(1) 解析に失敗したレスポンスをどう扱うか。**
NFR-003 は「未知のレスポンス構造に遭遇しても停止せず、縮退して動作を続ける」と定める。
縮退したこと自体は動作を守るが、**なぜ失敗したかを後から調べる材料が無ければ追随できない**。
素直な解決は「失敗したレスポンスをそのまま残す」だが、`/kcsapi/` のレスポンスには
提督名・`api_member_id` などが含まれ、リクエストには `api_token` が含まれる。
これは C-04（取得したデータを外部に出さない・認証情報をログに出力しない）に直接触れる。

**(2) テストのフィクスチャをどう用意するか。**
パース層のテストには本物に近い入力が要る。しかし実測したレスポンスをそのまま
`tests/fixtures/` に置けば、**個人情報が public リポジトリ（C-07）のコミット履歴に永久に残る**。
C-07 は「履歴からの完全な削除は事実上不可能であり、`git rm` では消えない」と明記している。

2 つを貫く難所は C-03 である。**艦これの API は非公開であり、どのフィールドが識別子なのか
完全には分からない。** したがって「識別子を列挙して消す」方式は、
消し漏れが無いことを原理的に証明できない。

### 調査した事実

いずれも 2026-08-02 に各リポジトリを実際に読んで確認した。

**poi（[poooi/poi](https://github.com/poooi/poi)）—— 実測データが匿名化されずにコミットされている。**

- `views/redux/info/__tests__/__fixtures__/` に 48 件・計 864KB の `/kcsapi/` レスポンスが置かれている
  （[ディレクトリ](https://github.com/poooi/poi/tree/master/views/redux/info/__tests__/__fixtures__)）
- [`api_port_port_typical.json`](https://github.com/poooi/poi/blob/master/views/redux/info/__tests__/__fixtures__/api_port_port_typical.json)
  の `api_basic` には実在の `api_member_id`・`api_nickname`（提督名）・`api_nickname_id`・
  自由記述の `api_comment` がそのまま入っている。48 件中 10 件が `api_member_id` を含み、
  値はすべて同一（同一プレイヤーの実データ）
- さらに同じ値が Jest スナップショット 2 件（`__snapshots__/*.snap`）にも複製されている。
  **実データをフィクスチャにすると、派生成果物に二次的にコピーが増える**
- これらは 2026-01-23 の [PR #2627](https://github.com/poooi/poi/pull/2627) 以降で追加されている。
  `api_token` は含まれない（トークンはレスポンスではなくリクエスト側にあるため）

**KancolleSniffer（[fujieda/KancolleSniffer](https://github.com/fujieda/KancolleSniffer)）—— 境界で除去し、実ログは別リポジトリに置いている。**

- [`Privacy.cs`](https://github.com/fujieda/KancolleSniffer/blob/master/KancolleSniffer/Privacy.cs) が
  `api_token` / `api_btime` を URL・リクエストから、`api_member_id` と
  `api_(nick)name` + `api_(nick)name_id` の組をレスポンスから正規表現で削除する
- [`Main.cs`](https://github.com/fujieda/KancolleSniffer/blob/master/KancolleSniffer/Main.cs) の
  `ProcessRequest` は、セッションを組み立てた**直後**に `Privacy.Remove(s)` を呼び、
  そのあとでデバッグログ書き出しと本処理に渡す。**除去が最も外側にあり、
  内側のどの経路にも生データが流れない**。デバッグログ自体も既定では無効
- バグ報告用の `error.log`（[`ErrorLog.cs`](https://github.com/fujieda/KancolleSniffer/blob/master/KancolleSniffer/ErrorLog.cs)）も
  同じ除去を通してから出力する
- テストが読む実ログは本体リポジトリに無く、
  [`.gitmodules`](https://github.com/fujieda/KancolleSniffer/blob/master/.gitmodules) により
  `git://git.osdn.net/gitroot/kancollesniffer/logs.git` という**別リポジトリの submodule** になっている。
  2026-08-02 の実測では `osdn.net` / `git.osdn.net` が名前解決できず（SERVFAIL）、取得できなかった
- **除去は列挙式であり、取りこぼしが実在する。** 上記 poi の実データに含まれる
  `api_comment`（提督の自由記述）と `api_user_name` は、`Privacy.cs` の正規表現の対象外である

**ElectronicObserver（[andanteyk/ElectronicObserver](https://github.com/andanteyk/ElectronicObserver)）—— 生のまま保存する。既定は無効。**

- [`APIObserver.cs`](https://github.com/andanteyk/ElectronicObserver/blob/develop/ElectronicObserver/Observer/APIObserver.cs)
  の `SaveRequest` / `SaveResponse` は、リクエスト・レスポンスの本文を**一切加工せず**
  ユーザー指定のディレクトリへ書き出す
- [`Configuration.cs`](https://github.com/andanteyk/ElectronicObserver/blob/develop/ElectronicObserver/Utility/Configuration.cs)
  の既定は `SaveReceivedData = false` / `SaveRequest = false` / `SaveResponse = true`。
  つまり**既定では何も保存されず**、有効化して初めて書き出される
- develop ブランチにテストプロジェクトは存在せず、フィクスチャもコミットされていない

**匿名化・仮名化の限界（一般論）。**

- EU 第 29 条作業部会 [Opinion 05/2014 (WP216)](https://ec.europa.eu/justice/article-29/documentation/opinion-recommendation/files/2014/wp216_en.pdf)
  は、**仮名化は匿名化ではない**と明示する。識別子を別の値に置き換えても
  singling out / linkability / inference のリスクは残る
- [NIST SP 800-188](https://csrc.nist.gov/pubs/sp/800/188/final) も、直接識別子の除去だけでは足りず、
  準識別子の変換や**合成データの生成**を techniques として並置している
- 本件では、識別子の一覧そのものが不明（C-03）である。つまり
  **「準識別子の扱いが難しい」以前に、「直接識別子を列挙しきれたか」すら検証できない**

**「うっかり混入」を止める道具。**

- [gitleaks](https://github.com/gitleaks/gitleaks) は正規表現ベースの検出器で、pre-commit にも CI にも置ける。
  カスタムルールを TOML で追加できる
- GitHub の [secret scanning / push protection](https://docs.github.com/en/code-security/secret-scanning/introduction/about-secret-scanning)
  は public リポジトリで無償だが、**検出するのは提携プロバイダ等の既知パターン**である。
  艦これの `api_token` や提督名は対象にならない

**Rust のフィクスチャの置き方。**

- [Cargo のプロジェクト構成](https://doc.rust-lang.org/cargo/guide/project-layout.html)では
  結合テストは `tests/`。データファイルは `tests/fixtures/` に置き、
  `include_str!` などで読むのが一般的な形である
- スナップショットテストの [`insta`](https://docs.rs/insta/latest/insta/) は `redactions` 機能で
  特定の値を伏せられるが、**これも伏せる場所を人が指定する列挙式**であり、C-03 の下では同じ限界を持つ

> 通常の観測データを保存する際の同じ原則（許可リスト方式）は
> [ADR-0021](0021-data-persistence.md) の原則 2 にある。両者は同じ根拠に立つ。

## 決定

1. **生の `/kcsapi/` レスポンス・リクエストを、既定ではどこにも保存しない。**
   解析に失敗したときに残すのは、値を捨てて構造だけにした**構造サマリ**（失敗した API パス・
   失敗の種類・失敗位置の JSON パス・その位置の型名と長さ・兄弟キーのキー名）だけとする。
2. 生データの保存は**ユーザーが明示的に有効化したときに限る**。
   保存先は release では OS のアプリデータ領域（NFR-008 の「ユーザーから辿れる場所」）、
   **debug では リポジトリ配下の `.local/`（git 管理外）**とする。
   開発中に OS のアプリデータ領域を掘るのは扱いづらいため。
   **リポジトリ配下に置ける根拠は、コミットの阻止を場所ではなく CI に置いているからである**（下記 3 の補足参照）。
   ユーザーが一括削除できることを必須要件とする。
3. **テストフィクスチャは合成データのみとし、生成器（Rust コード）の出力とバイト一致することを
   CI で強制する。** 実測データはリポジトリに一切コミットしない。
   実測データを使うテストは、git 管理外のローカルディレクトリを読む**任意実行のテスト**として
   分離し、CI では実行しない。

除去（マスク）は**注入スクリプトから Rust コアへ渡ったあとの最も外側**、
つまりパース層に入る前の一点で行う。それより内側に生データを流さない。

### 補足: 拒否リストは二次防御としてなら置く

KancolleSniffer 型の拒否リストを却下したのは**一次防御として使えない**からであり、
**構造そのものは正しい**（除去を最も外側の一点に置く点は既に取り込んでいる）。

一方で、**許可リストを通過した後の最後の網としては有効である。**

- 許可リスト（[ADR-0021](0021-data-persistence.md) 原則 2）を一次防御とする
- その通過後に、既知の識別子（提督名・`api_member_id` 等）を落とす拒否リストを二次防御として置く

効くのは次の場面である。**許可したフィールドが、ゲーム更新後に個人情報を含み始めたとき。**
たとえば自由記述の枠が増設された場合、許可リストはそれを通してしまう。

拒否リストは「完全性を保証するもの」としては使えないが、
「**既知の危険を確実に止めるもの**」としては機能する。

## 検討した選択肢

### 論点 1: 解析に失敗したレスポンスを保存するか

#### 案 A1: 構造サマリを既定とし、生データは明示的な有効化に限る（採用）

- 概要: 失敗時は値を持たない構造サマリのみを残す。生データの保存は既定で無効で、
  ユーザーが有効にしたときだけアプリデータ領域に書かれ、ユーザーが消せる。
- 利点:
  - **構造サマリには値が入らないため、マスク漏れという事象が起きない。**
    どのフィールドが識別子かを知らなくてよい（C-03 に耐える）
  - NFR-003 の追随に必要な情報（どの API の・どの位置で・何が想定と違ったか）は残る
  - 生データが要る場面（構造サマリでは足りない不具合）にも、ユーザーの明示的な同意の下で到達できる
  - 既定無効・保存先はユーザーから辿れる・削除できる、の 3 点は ElectronicObserver の
    運用（既定 `SaveReceivedData = false`）から取り込んだ
- 欠点:
  - 値に依存する不具合（想定外の値域・エンコード）は構造サマリだけでは分からない
  - キー名と文字列長は残るため、漏れる情報が厳密にゼロではない。
    これは受け入れる（キー名は `^api_[a-z0-9_]+$` に一致するものだけをそのまま残し、
    一致しないものは長さと文字種に落とす）

#### 案 A2: 何も保存しない

- 概要: 失敗しても縮退するだけで、記録を一切残さない。
- 利点: 情報が出る経路が構造的に存在しない。最も安全。
- 却下理由: NFR-003 は「止まらないこと」を求めるが、止まらないまま原因が分からなければ
  仕様変更に追随できず、C-03 の前提そのものが回らなくなるため。

#### 案 A3: 生データをマスクして常に保存する（KancolleSniffer 方式）

- 概要: `Privacy.cs` と同様に、除去対象を列挙した正規表現で消してから保存する。
- 利点: 除去を最も外側に置く構造は正しく、内側の全経路が自動的に守られる。
  実際に長期間運用されている前例がある。
- 却下理由: 列挙式であり、実データに存在する `api_comment` / `api_user_name` が
  現に対象から漏れていることを確認したため。C-03 の下では「列挙しきれた」ことを検証できない。
  （**除去を最も外側の一点に置くという構造は、案 A1 に取り込んでいる**）

#### 案 A4: 生のまま保存する。既定は無効（ElectronicObserver 方式）

- 概要: 加工せずユーザー指定のディレクトリへ書き出す。既定は無効。
- 利点: 実装が単純で、原因調査に必要な情報が完全に残る。
- 却下理由: 有効にした瞬間に `api_token` と提督名が平文でディスクに残り、
  C-04 の「認証情報をログに出力しない」に正面から反するため。
  （**既定無効・保存先の明示という運用は、案 A1 に取り込んでいる**）

### 論点 2: テストのフィクスチャをどう用意するか

#### 案 B1: 合成フィクスチャのみ。生成器の出力とのバイト一致を CI で検証（採用）

- 概要: フィクスチャを Rust の生成器コードから決定的に生成し、生成物を `tests/fixtures/` にコミットする。
  CI は生成器を再実行して差分が出たら fail させる。
  実測データを読むテストは `#[ignore]` 相当の任意実行として分離し、
  データは git 管理外のローカルディレクトリに置く。
- 利点:
  - **検証したい性質が「マスク漏れが無いこと」（証明不能）から
    「生成器の出力と一致すること」（機械的に判定可能）に置き換わる。**
    手で置いた実データは生成器から出ないため、必ず CI が落ちる
  - どのフィールドが識別子かを知る必要がない（C-03 に耐える）
  - 境界値・異常系を意図して作れる。実測データは「たまたま観測できた形」しか含まれない
  - 実データによる検証は、ローカルの任意実行テストとして併用できる
- 欠点:
  - 生成器の想定が誤っていれば、テストは「誤った想定」を検証し続ける。
    実データとの突き合わせはローカルでしか回らない
  - 生成器の維持コストが要る

#### 案 B2: 実測データを匿名化してコミットする

- 概要: 実測レスポンスから識別子を置換・除去してから `tests/fixtures/` に入れる。
- 利点: 本物の構造をそのまま検証できる。生成器が要らない。
- 却下理由: C-03 により「匿名化しきれた」ことを検証できず、C-07 により失敗が取り返しのつかない事故になるため。
  poi では匿名化されないままコミットされ、スナップショットにも複製されている。

#### 案 B3: 実測データを別リポジトリの submodule に置く（KancolleSniffer 方式）

- 概要: ログを本体とは別のリポジトリに分け、submodule として参照する。
- 利点: 本体のコミット履歴が汚れない。本物のログでテストできる。
- 却下理由: そのリポジトリが public なら公開されることは同じで、private なら第三者がテストを再現できず、
  ADR-0005 の「第三者が検証できる」という公開の主目的を失うため。
  加えて外部ホスティングの寿命に依存する（当該 submodule は 2026-08-02 時点で取得不能）。

#### 案 B4: 実測データをローカルにだけ置き、そこでだけテストする

- 概要: git 管理外のディレクトリに実データを置き、あるときだけ動くテストを書く。
- 却下理由: 単独では CI で一切検証されず、開発機ごとに結果が変わるため。
  **ただし案 B1 の補助としては有効であり、任意実行テストとして併用する。**

## 決め手

**「マスク漏れが無いこと」は C-03 の下では証明できないため、
検証したい性質を「値を持たない」「生成器の出力と一致する」という機械的に判定可能なものに置き換えた。**
その代わりに、本物のレスポンスで CI を回せるという再現性と、値に依存する不具合の調査しやすさを捨てた。

## 影響

- 実装への影響:
  - パース層は、失敗時に構造サマリを組み立てる責務を持つ。
    [ADR-0018](0018-dependencies.md) で `thiserror` を採ったのはこの前提と噛み合う
  - 生データの除去は、Rust コアの入口（パース層に入る前）の一点に置く。
    それより内側に生データを渡す実装は本 ADR 違反として扱う
  - フィクスチャ生成器と、その出力を検証する CI ジョブを新設する
  - **仕組みで防ぐための具体策**（運用の注意ではなく、機械的に落ちるもの）:
    1. **フィクスチャは生成器の出力とバイト一致していなければ CI が fail する**（本決定 3）。
       手で置いた実データは必ず検出される
    2. **開発中の保存先は `.local/`（git 管理外）に固定する。**
       ここに置いたものがコミットされないことの保証は `.gitignore` ではなく **3 の判定**にある。
       `.gitignore` は `git add -f` で、pre-commit は無効化で越えられるため。
       **したがって 3 を実装する前に `.local/` を使い始めてはならない。順序は CI が先である**
    3. **フィールド名ではなく「ファイルの形」で弾く。** 追跡対象ファイルを走査し、
       `svdata=` で始まるもの、および `api_result` と `api_data` を同時に持つ JSON が
       生成器の出力以外に存在したら fail させる。**どのフィールドが識別子かを知らなくてよい**
    4. gitleaks を pre-commit と CI に置き、`api_token` を検出するカスタムルールを足す。
       GitHub の push protection は既知パターンのみを見るため、補助にとどまる
    5. `.gitignore` は `git add -f` で越えられるため補助でしかない。
       **pre-commit も無効化できるため、判定の正は CI に置く**
- ドキュメントへの影響（いずれも**人間の承認が必要**）:
  - [architecture.md](../spec/architecture.md)「データの持ち方」に、生データを保持しないことと
    除去を行う境界の位置を追記する
  - [docs/spec/external/](../spec/external/) に、生データ保存の有効化・保存先・削除という
    ユーザーから見える振る舞いを定義する。対応する FR が [requirements.md](../spec/requirements.md) に無いため、
    要求の追加が要る
  - テストとフィクスチャの規約は [docs/guidelines/](../guidelines/) に 1 本起こす
- 取り消す場合のコスト:
  - 生データを保存する側へ倒すのは容易（機能追加で済む）
  - **フィクスチャを実測データへ切り替える方向は事実上不可逆。**
    一度コミットすれば C-07 のとおり履歴から消せない
