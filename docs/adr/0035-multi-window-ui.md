# ADR-0035: 情報表示をマルチウィンドウ方式にする

- ステータス: Accepted
- 日付: 2026-08-09
- 決定者: プロジェクトオーナー
- 関連: ADR-0016 / docs/spec/external/game-screen.md

## 背景と課題

要求は B（艦隊）・C（タイマー）・D（出撃支援）・E（記録）・F（任務）と広く、
すべての情報を 1 つの画面に収めることは現実的でない。
外部仕様のドラフトは「1 ウィンドウ + 情報パネル（右 / 下 / 非表示）」を仮置きしていたが、
情報量に対してパネル 1 枚では足りず、ウィンドウ構成を決める必要があった。

前提として、技術構成は Tauri + Rust + React（ADR-0016）であり、
Tauri は複数ウィンドウを標準でサポートする。状態は Rust コアからイベントで
各ウィンドウに配る構造のため、ウィンドウが増えても状態管理の構造は変わらない。

## 決定

ゲーム画面専用のメインウィンドウと、機能グループ単位の情報ウィンドウに分ける。
情報ウィンドウは独立した OS ウィンドウとし、配置はユーザーが OS のウィンドウ操作で行う。
1 ウィンドウ 1 機能グループとし、複数グループの合体表示（タブ・ドッキング）は提供しない。

## 検討した選択肢

### 案 A: マルチウィンドウ（採用）

- 概要: メインウィンドウはゲーム専用。情報は機能グループごとに別の OS ウィンドウで表示する
- 利点:
  - レイアウト管理（移動・リサイズ・重なり順）を OS に委ねられ、自前実装が不要になる
  - 情報ごとに独立してサイズを決められ、情報量の問題が解消する
  - マルチディスプレイ環境と相性が良い
  - 「常に手前」をウィンドウ単位で提供できる
- 欠点:
  - ウィンドウごとに WebView プロセスが増え、メモリを消費する（特に Windows の WebView2）
  - ウィンドウが散らかりうる。開閉・復元の管理をアプリが持つ必要がある

### 案 B: 1 ウィンドウ + ドッキングパネル（ElectronicObserver 型）

- 概要: 1 つのウィンドウ内でパネルを分割・ドッキングして自由配置する
- 利点: ウィンドウが 1 つにまとまり、全体を 1 操作で移動できる
- 欠点: 分割・ドッキング UI は自前実装になり、UI 実装として最も重い部類
- 却下理由: ドッキング UI の実装コストが機能そのものの開発を圧迫する

### 案 C: 1 ウィンドウ + 固定の情報パネル（旧ドラフト）

- 概要: ゲーム画面の右または下に情報パネルを 1 枚置き、
  すべての情報グループをタブ等で切り替えて収める（ドラフトの仮置き案）
- 却下理由: 表示できる情報量が不足し、タブ切り替えが常態化して「常時確認できる」目的に反する

## 決め手

レイアウト管理の実装コストを丸ごと消すために、
ウィンドウごとに WebView プロセスが増えるメモリ消費を受け入れた。
常時開くウィンドウは数枚と想定し、NFR-006（長時間起動でメモリが増え続けない）の範囲で許容する。

## 影響

- 実装への影響: Tauri のウィンドウを情報ウィンドウごとに生成する。
  状態同期は Rust コアからのイベント配信のままで、ウィンドウ間の直接通信は作らない
- ドキュメントへの影響（更新が必要な spec）: docs/spec/external/game-screen.md（ウィンドウ構成の全面改稿）、
  docs/spec/external/fleet-view.md / timers.md（表示先の明記）、
  docs/spec/architecture.md（UI が複数ウィンドウに分かれることの明記）、
  docs/spec/requirements.md（FR-007 の語の更新）、docs/spec/glossary.md（用語追加）
- 取り消す場合のコスト: 外部仕様と UI 実装の書き直し。
  ウィンドウ状態の保存データ（開閉・位置・大きさ）も作り直しになる

## 未解決事項

  要望が出た時点で本 ADR を見直す
- 情報ウィンドウの既定サイズ・位置（docs/spec/external/game-screen.md の未解決事項）
