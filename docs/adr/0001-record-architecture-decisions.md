# ADR-0001: 意思決定を ADR として記録する

- ステータス: Accepted
- 日付: 2026-08-01
- 決定者: プロジェクトオーナー
- 関連: [ADR-0002](0002-documentation-structure.md), [ADR-0003](0003-agent-driven-development.md)

## 背景と課題

本プロジェクトの実装は AI エージェントが行う（[ADR-0003](0003-agent-driven-development.md)）。
エージェントはセッションをまたいで文脈を保持しないため、
「なぜこの構成なのか」「なぜその案を採らなかったのか」が文書に残っていないと、
以下が繰り返し起きる。

- 一度否決した案を再提案する
- 決定の前提を知らずに、前提を壊す変更を入れる
- 人間が毎回同じ背景説明を書かされる

仕様書（spec）は「いまどうなっているか」を書く場所であり、経緯を書くと肥大化する。
決定の記録は別の器が要る。

## 決定

設計上の意思決定を **ADR（Architecture Decision Record）** として
`docs/adr/NNNN-english-kebab-title.md` に 1 決定 1 ファイルで記録する。
形式は [MADR](https://adr.github.io/madr/) の簡略版とし、
`Accepted` になった ADR の本文は書き換えない（追記型・不変）。

## 検討した選択肢

### 案 A: ADR を導入する（採用）

- 概要: 決定ごとに独立したファイルを追記していく。
- 利点: 決定単位で参照でき、エージェントに「関連 ADR だけ」を読ませられる。
  git 履歴と別に、意図が自然言語で残る。
- 欠点: 起票の手間。粒度の判断が必要。

### 案 B: 決定を仕様書内に「経緯」節として書く

- 概要: `docs/spec/` の各ファイルに背景節を設ける。
- 利点: ファイル数が増えない。
- 欠点: 仕様が経緯で埋まり「現在の正解」が読み取りにくくなる。
  却下案の記録は仕様の更新時に消えてしまう。
- 却下理由: spec の第一の読者は実装エージェントであり、
  現在形の記述だけが並んでいる状態を保ちたいため。

### 案 C: git のコミットメッセージ / PR 説明に残す

- 概要: 決定はコミット履歴を辿れば分かる、という運用。
- 却下理由: 検索性が低く、エージェントに読ませる単位として使いにくい。
  また「今も有効な決定か」がコミット履歴からは判断できない。

## 決め手

エージェント駆動開発では、**必要な文脈を必要なだけ渡せる粒度**が最重要である。
ADR は「1 決定 = 1 ファイル = 1 参照単位」となり、この要件に最も合う。

## 影響

- 実装への影響: なし（ドキュメント運用のみ）。
- ドキュメントへの影響: `docs/adr/` を新設。`docs/adr/README.md` に一覧を維持する。
- 取り消す場合のコスト: 低。書いた ADR はそのまま設計メモとして残る。
