# ADR-0006: 仕様を外部仕様・内部仕様・ガイドラインに分割する

- ステータス: Accepted（`internal/` は Superseded by [ADR-0008](0008-code-as-source-of-truth.md)、`guidelines/` の配置は Superseded by [ADR-0010](0010-top-level-doc-layout.md)）
- 日付: 2026-08-01
- 決定者: プロジェクトオーナー
- 関連: [ADR-0002](0002-documentation-structure.md)（本 ADR は 0002 を置き換えず、`spec` 層を細分化する）, [ADR-0003](0003-agent-driven-development.md)

## 背景と課題

[ADR-0002](0002-documentation-structure.md) で notes / spec / adr の 3 層を定めたが、
`docs/spec/` が単一の平坦なディレクトリのままだと、性質の異なる記述が混ざる。

- 「遠征の残り時間を分単位で表示する」（ユーザーに見える振る舞い）
- 「観測したデータを SQLite に保存する」（実装の構造）
- 「エラー時は例外を握りつぶさない」（横断的なルール）

これらは**変更したときの承認の重さが違う**。1 つ目を変えるのは仕様変更であり
人間の判断が要るが、2 つ目は外部の振る舞いを保ったまま差し替えてよい。
混在していると、エージェントは「これは勝手に変えてよい記述か」を判断できず、
安全側に倒して何も変えないか、危険側に倒してユーザー可視の振る舞いを勝手に変える。

## 決定

`docs/spec/` を以下に細分化する。

```
docs/spec/
├── overview.md / requirements.md / constraints.md / glossary.md   ← 要求層（何が必要か）
├── external/     外部仕様: ユーザーから見える振る舞い
├── internal/     内部仕様: それをどう実現するか
└── guidelines/   ガイドライン: 個別機能に属さない横断ルール
```

あわせて、**変更時の承認境界**をディレクトリに対応づける。

| 場所 | 内容 | 変更するとき |
| --- | --- | --- |
| 要求層 | 何が必要か | **人間の承認が必要** |
| `external/` | ユーザーから見える振る舞い | **人間の承認が必要** |
| `internal/` | 実装の構造 | 外部仕様を変えない限り、エージェントが更新してよい |
| `guidelines/` | 横断ルール | **人間の承認が必要**（影響が広いため） |

内部仕様は技術構成に従属するため、[ADR-0004](0004-defer-tech-stack-decision.md) が
解消されるまで `internal/` と `guidelines/` は原則として空のままとする。

## 検討した選択肢

### 案 A: external / internal / guidelines の 3 分割（採用）

- 概要: 上記のとおり。
- 利点:
  - **エージェントの裁量範囲がパスで表現される。** 「`internal/` は自由に、
    `external/` は承認を得てから」と指示でき、判断をエージェントに委ねずに済む。
  - 技術構成が変わったとき、書き直す範囲が `internal/` に閉じる。
    外部仕様は技術に依存しないため生き残る（[ADR-0004](0004-defer-tech-stack-decision.md) の保留期間中でも
    外部仕様は書き進められる、という副次的な利点がある）。
  - レビューの粒度が揃う。人間は `external/` の差分だけ精読すればよい。
- 欠点: 1 機能の記述が 2 ファイルに分かれる。相互リンクの維持コストが生じる。

### 案 B: 機能ごとに 1 ファイルとし、その中を「外部」「内部」の節で分ける

- 概要: `features/expedition-timer.md` の中に両方書く。
- 利点: 1 機能 1 ファイルで探しやすい。リンク維持が不要。
- 欠点: 承認境界がファイル単位で表現できない。差分レビュー時に、
  ユーザー可視の変更と内部リファクタが同じファイルに混ざる。
- 却下理由: [ADR-0002](0002-documentation-structure.md) と同じ思想
  （**運用ルールではなく構造で守る**）を貫くため。節見出しは守り忘れるが、
  ディレクトリは守り忘れない。

### 案 C: 分割せず現状維持

- 却下理由: 内部仕様を書き始めた時点で確実に破綻する。
  空のうちに枠を作るほうが安い。

## 決め手

エージェント駆動開発（[ADR-0003](0003-agent-driven-development.md)）では、
**「どこまで勝手に変えてよいか」を明示できることの価値が大きい**。
案 A はそれをディレクトリ構造として表現でき、指示のたびに説明する必要がなくなる。

## 影響

- ドキュメントへの影響:
  - `docs/spec/{external,internal,guidelines}/` を新設し、それぞれに README とテンプレートを置く。
  - 既存の `docs/spec/_template-feature.md` は `docs/spec/external/_template.md` に移し、
    内部仕様に属する記述（データ取得元など）を `internal/_template.md` 側へ分離する。
  - `docs/README.md` / `CLAUDE.md` / `write-spec` スキルの記述を更新する。
- 実装への影響: なし（実装は未着手）。
- 取り消す場合のコスト: 低（ファイル移動とリンク修正のみ）。
