# ADR-0014: 当分の間 `main` に直接コミットする

- ステータス: Accepted
- 日付: 2026-08-02
- 決定者: プロジェクトオーナー
- 関連: [ADR-0003](0003-agent-driven-development.md), [ADR-0005](0005-publish-as-oss.md)

## 背景と課題

ブランチと Pull Request は、**並行作業の隔離**と**非同期レビュー**のための仕組みである。
現状はそのどちらも存在しない。

- 実装は未着手で、作業しているのは 1 人（+ 1 エージェント）のみ
- レビューは対話の中で即時に行われており、PR を経由する必要が無い
- CI がまだ無いため、マージ前に自動検証すべきものも無い

一方で、**エージェントの既定の挙動はブランチを切ること**である。
何も書かれていなければ、エージェントは作業のたびに feature ブランチを作り、
PR を提案する。これは現状の作業実態に対して手間が増えるだけになる。

## 決定

**当分の間、`main` に直接コミットする。ブランチと PR を作らない。**

エージェントはこの規約に従い、**既定のブランチ運用を適用しない**。
[CLAUDE.md](../../CLAUDE.md) と [CONTRIBUTING.md](../../CONTRIBUTING.md) に明記する。

### 再検討する契機

以下のいずれかが起きた時点で、この決定を見直す（新しい ADR を起票する）。

- 複数のエージェントが**並行して**作業するようになった
- 外部の貢献者からの Pull Request を受け入れる
  （[ADR-0005](0005-publish-as-oss.md) の未解決事項）
- CI を導入し、マージ前の自動検証が必要になった

## 検討した選択肢

### 案 A: `main` 直コミット（採用）

- 利点: 手数が最小。レビューが対話で完結している現状に合う。
  履歴が直線になり、経緯を追いやすい。
- 欠点: 壊れた状態が `main` に入りうる。1 コミットの粒度を保つ規律が要る。

### 案 B: feature ブランチ + PR（自分でマージ）

- 概要: 変更ごとにブランチを切り、PR を経由する。
- 却下理由: レビュアーと作業者が同一で、レビューは既に対話で終わっている。
  PR は形式だけになり、承認を待つ時間が増える。

### 案 C: 変更の規模で使い分ける

- 却下理由: 「大きい変更」の線引きが必要になり、判断のたびに迷いが生じる。
  エージェントに委ねれば揺れる。**規約は例外なしのほうが守られる。**

## 決め手

**レビューの即時性を得るために、変更の隔離を捨てた。**
隔離が必要になるのは並行作業か外部貢献が始まってからであり、いまはどちらも無い。

## 影響

- エージェントはコミット前にブランチを作らない。既定の挙動を明示的に上書きする。
- `main` が常に公開状態であるため、**壊れたまま push しない**規律が要る。
  1 コミット 1 目的（[CLAUDE.md](../../CLAUDE.md) §4）の徹底で担保する。
- 取り消す場合のコスト: 低。次の変更からブランチを切ればよい。
