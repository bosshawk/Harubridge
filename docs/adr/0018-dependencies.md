# ADR-0018: 依存ライブラリを選定する

- ステータス: **Accepted**（リンタの選定のみ Superseded by [ADR-0019](0019-linter.md)。他の依存は有効）
- 日付: 2026-08-02
- 決定者: プロジェクトオーナー
- 関連: [ADR-0016](0016-tech-stack.md)（本 ADR が未解決事項「Rust と TypeScript の間の型の受け渡し方法」を解消する）,
  [ADR-0017](0017-llm-endpoint.md)

## 背景と課題

[ADR-0016](0016-tech-stack.md) で Tauri + Rust + React を決めたが、
その内側のライブラリは未選定だった。実装に入る前に確定させる。

判断材料として、**2026-08-02 時点の crates.io / npm の実測値**（安定版・DL 数）を用いた。
「最新か」「デファクトか」を記憶ではなく実測で確認している（[C-03](../spec/constraints.md) の精神）。

## 決定

### Rust

| 用途 | 採用 | 安定版 | DL/月 |
| --- | --- | --- | --- |
| フレームワーク | `tauri` | 2.11.5 | 894 万 |
| 非同期 | `tokio` | 1.53.1 | 1.99 億 |
| シリアライズ | `serde` | 1.0.229 | 2.53 億 |
| エラー型 | `thiserror` | 2.0.19 | 3.10 億 |
| エラー伝播 | `anyhow` | 1.0.104 | 1.85 億 |
| HTTP | `reqwest` | 0.13.4 | 1.54 億 |
| ログ | `tracing` | 0.1.44 | 1.69 億 |
| **永続化（記録）** | **`rusqlite`** | 0.40.1 | 2811 万 |

`thiserror` と `anyhow` を併用する。パース層など**ライブラリ的な層は `thiserror` で
エラーを型として定義**し、アプリの端では `anyhow` で伝播させる。
NFR-003（未知の構造でも停止せず縮退）は、エラーを型で扱えることが前提になる。

### Tauri 公式プラグイン

| プラグイン | 安定版 | 対応する要求 |
| --- | --- | --- |
| `notification` | 2.3.3 | FR-023 / 024 / 025 |
| `window-state` | 2.4.1 | FR-003 |
| `store` | 2.4.4 | 設定の保存 |
| `log` | 2.9.0 | ログ |
| `dialog` | 2.7.2 | FR-004（保存先の選択） |
| `single-instance` | 2.4.3 | 二重起動の防止 |

**`tauri-plugin-sql` と `tauri-plugin-http` は採用しない。**
どちらも**フロントエンドから直接**データベース／HTTP を叩くための仕組みであり、
[architecture.md](../spec/architecture.md) の
「UI は Rust コアから受け取った状態のみを描画する」に反する。
Rust 側で `rusqlite` と `reqwest` を直接使う。

### 型の受け渡し

**`tauri-specta` v2 を採用する。** `specta` ともにバージョンを `=` で完全固定する。

```
specta@=2.0.0-rc.25
tauri-specta@=2.0.0-rc.25
specta-typescript@0.0.12
```

### フロントエンド

| 用途 | 採用 | 版 | DL/週 |
| --- | --- | --- | --- |
| 言語 | TypeScript | 7.0.2 | 2.55 億 |
| UI | React | 19.2.8 | 1.62 億 |
| ビルド | `vite` | 8.2.0 | 1.46 億 |
| 状態管理 | `zustand` | 5.0.14 | 4953 万 |
| テスト | `vitest` | 4.1.10 | 8726 万 |
| リンタ / 整形 | `@biomejs/biome` | 2.5.6 | 1191 万 |

Rust 側のテストは `cargo test`、静的解析は `rustfmt` + `clippy`（警告をエラー扱い）。

**UI コンポーネントライブラリは選定しない。**
表の列構成や状態の見せ方は外部仕様（`external/fleet-view.md` 等）が確定してから決める。
先に選ぶと、ライブラリの都合に仕様が引きずられる。

## 検討した選択肢

### 永続化: `rusqlite` を採用、`sqlx` を却下

- `sqlx`（0.9.0 / 3195 万）はコンパイル時にクエリを検証できるが、
  **ビルド時に DB か `sqlx prepare` のキャッシュが必要**で CI が一段複雑になる
- `rusqlite`（0.40.1 / 2811 万）は非同期に対応しないが、
  **デスクトップアプリではそれが問題になりにくい**
- DL 数はほぼ互角であり、前例の量では差がつかなかった
- **却下: `native_db`**（0.8.2 / **8 千**）。Rust の型をそのまま保存でき思想的には最も整合するが、
  採用規模が 3 桁小さい。[ADR-0003](0003-agent-driven-development.md) の体制では前例の薄さが直接リスクになる
- **却下: `redb`**（4.1.0 / 344 万）。KV ストアであり、時系列の集計（FR-042 など）に SQL が使えない

### 型の受け渡し: `tauri-specta` を採用、`ts-rs` を却下

当初は「`tauri-specta` の v2 が 2 年以上 RC である」ことを理由に
`ts-rs`（12.0.1 / 410 万）を推していた。**これは誤りだった。**

- **Tauri v2 に対応するのは `tauri-specta` v2 のみで、v1 は "Unsupported" と公式に明記されている。**
  RC は「安定版に至っていない」のではなく、**v2 対応版が RC しかない**という構造である
- 実測でも RC が事実上の本番版として使われている
  （rc.21: 56.5 万 DL、rc.20: 15.6 万、rc.25: 10.1 万 に対し、安定版 1.0.2 は **2.9 万**）
- 決定的な差は **型付きイベント**。`ts-rs` は型定義のエクスポートのみで、
  **Tauri のイベントを一切カバーしない**。
  [architecture.md](../spec/architecture.md) では Rust コアから UI へ状態を push する経路が主役であり、
  **そこが無型のまま残るのは選定の趣旨に反する**
- `collect_commands!` によりコマンドの登録と型の生成が同一のリストから出るため、
  「登録したが型を出し忘れた」というズレが構造的に起きない
- **却下: `taurpc`**（0.8.2 / **2,582**）。採用規模が小さすぎる

**リスクと退避**: ドキュメントが「ベータ期間中はバージョンを `=` で固定することが非常に重要」と
明記しているため、そのとおり完全固定する。
詰まった場合は `ts-rs` へ退避できる（Rust 側の型定義は残り、失うのは生成物のみ）。

### リンタ: `biome` を採用、`eslint` + `prettier` を却下

- 採用規模では `eslint`（1.53 億）+ `prettier`（1.17 億）が `biome`（1191 万）を 10 倍以上上回る
- それでも `biome` を採る理由は、**設定ファイルとツールが 1 つで済むこと**。
  [ADR-0003](0003-agent-driven-development.md) の体制では、
  **設定の分岐が少ないほどエージェントが誤設定する余地が減る**
- **この 1 項目だけは「前例の量」より「事故の起きにくさ」を優先した**。
  他の項目とは判断軸が異なることを明記しておく

### 状態管理: `zustand` を採用

- `jotai`（561 万）の約 9 倍の採用規模
- **却下: `@tanstack/react-query`**（6184 万）。サーバ状態の同期が主目的であり、
  Rust から IPC で届く本アプリのデータとは役割が合わない

## 決め手

**実測値で「デファクトかどうか」を確認したうえで、
ドメインの要求（型付きイベント・SQL による集計）が満たされるものを選んだ。**

例外は `biome` の 1 項目のみで、そこは判断軸を変えたことを上に明記した。

## 影響

- [ADR-0016](0016-tech-stack.md) の未解決事項「Rust と TypeScript の間の型の受け渡し方法」が解消する
- FR-003（ウィンドウ状態の復元）と FR-023〜025（通知）は、
  公式プラグインの採用により実装量が大きく減る
- 取り消す場合のコスト: **項目により異なる。**
  永続化と型生成は実装が進むほど高くなる。リンタとフロントの周辺は低い
