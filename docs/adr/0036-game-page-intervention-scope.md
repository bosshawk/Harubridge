# ADR-0036: ゲームページへの介入を「表示のための CSS 注入」まで許し、それ以外は読み取りに徹する

- ステータス: Proposed
- 日付: 2026-08-16
- 決定者: 承認待ち（`Accepted` にする時点で承認者名に書き換える）
- 関連: docs/spec/architecture.md / docs/spec/constraints.md / docs/spec/external/game-screen.md

## 背景と課題

[architecture.md](../spec/architecture.md) は「**ゲームのページに副作用を与えない。
注入スクリプトは観測に徹する**」と定めている。この規律の下では、
[external/game-screen.md](../spec/external/game-screen.md) が約束している
「ゲーム画面の領域と、その下部の操作バーだけを表示する」を実現する手段が無い。

実機で 3 通りを試し、次が分かった（macOS / WKWebView、2026-08-16）。

| 埋め込む対象 | 描画 | 課金導線 |
| --- | --- | --- |
| 入口ページ `play.games.dmm.com/game/kancolle` | 別オリジンの `iframe` に入らない（`X-Frame-Options: SAMEORIGIN`） | — |
| ガジェット枠 `osapi.dmm.com/gadgets/ifr` | **描画されない**（音は出る） | 到達できない |
| ゲーム本体 `*.kancolle-server.com/kcs2/` | 描画され、操作でき、母港まで到達する | **購入確認が表示されない** |

課金の購入確認はポップアップではなく**ページ内のオーバーレイ**であり、
これを描くのは切り出した内側のフレームより外側である。
**DMM の階層を削ると、描画か課金導線のどちらかが必ず壊れる。**

したがって「入口ページを丸ごと読み込む」以外の選択肢が無く、
そのページは別オリジンの `iframe` に入らないため、
**ページに一切触れない限り、ゲーム画面だけを見せることはできない。**

既存ツールの実装も同じ結論に達している（2026-08-16 参照）。

| ツール | 方法 |
| --- | --- |
| poi (`assets/js/page-align.js`) | 入口ページを丸ごと読み、`<style>` を注入して DMM のヘッダ・広告・サイドバーを隠し、`#game_frame` を左上に固定する |
| ElectronicObserver (`Browser/BrowserViewModel.cs`) | 同じ。`#game_frame` を `position: fixed; top: 0; left: 0` に置き、`--game-frame-width: 1200px` / `--game-frame-height: 720px` を宣言する |
| logbook-kai | ブラウザを内蔵せず、プロキシとして観測するのみ。ゲームは通常のブラウザで遊ぶ |

**内側のフレームを切り出しているツールは無い。**

## 決定

ページへの介入を**「何を変えるか」で 4 段階に分け、いま許すのは 1 段目だけ**とする。
2 段目以降は**禁止ではなく、本 ADR で判断しない**。
必要が生じた時点で、**その用途ごとに個別の ADR で判断する。**

| 段階 | 何を変えるか | 例 | 現時点の扱い | 判断に効く制約 |
| --- | --- | --- | --- | --- |
| 1 | **見え方だけ**（手元の描画で完結する） | 表示のための CSS 注入 | **許す** | — |
| 2 | ページの**挙動** | ページの関数の置き換え、キー入力の抑止 | 個別に判断する | C-01 |
| 3 | ページが**受け取る内容** | ゲーム資材の差し替え | 個別に判断する | C-05 |
| 4 | ゲームサーバへ**送る内容** | Cookie の書き込み、リクエストの改変・再送 | 個別に判断する | C-02 |

1 段目として許すのは具体的に次である。入口ページを丸ごと読み込んだうえで、
`<style>` 要素を追加して配信元ページの装飾（ヘッダ・広告・サイドバー・余白）を隠し、
ゲーム画面の位置と大きさを整えること。

**本 ADR は [constraints.md](../spec/constraints.md) のいずれの制約も変更しない。**
段が上がるほど判断に要る材料が増え、4 段目については
同文書の未解決事項に挙がっている**利用規約の原文の確認**が前提になる。

なお**ページから値を読むだけの操作**（スクリーンショットのための `canvas` の読み取りなど）は
この段階分けの対象外である。ページを変えないため、別の論点として扱う。

## 検討した選択肢

### 案 A: 表示のための CSS 注入まで許す（採用）

- 概要: 入口ページを丸ごと読み、`<style>` の追加だけでゲーム画面を切り出して見せる
- 利点: DMM の階層が無傷なので**課金導線が壊れない**。
  実装が単純で、既存ツール 2 本と同じ方法であり、破綻したときの対処も参照できる。
  FR-002（表示倍率）の実現手段も同時に得られる
- 欠点: 配信元ページの構造（`#game_frame` などの id）に依存する。
  DMM 側のリニューアルで無効になりうる。ページに副作用を与えないという
  従来の規律を緩めることになる

### 案 B: マルチ Webview で操作バーとゲームを別 Webview にする

- 概要: 1 つの OS ウィンドウに Webview を 2 枚並べ、片方に入口ページ、
  片方に操作バーを置く。Webview をウィンドウより大きく取って位置をずらし、
  配信元ページの装飾を枠外へ追い出す
- 利点: ページに一切触れない。`X-Frame-Options` も課金導線も回避できる
- 欠点: `tauri` の `unstable` フィーチャが要る。
  ずらす量は配信元ページのレイアウトに依存するため、**結局ページ構造への依存は消えない**
- 却下理由: ページ構造への依存が消えないのに実装だけが重く、
  同じ依存を負うなら CSS のほうが意図が明示的で、破綻時に直しやすい

### 案 C: ゲーム画面だけを見せることを諦め、配信元ページをそのまま表示する

- 概要: 入口ページを等倍で表示し、操作バーは OS のメニューに置く
- 却下理由: [external/game-screen.md](../spec/external/game-screen.md) が約束している
  表示を実現できず、専用ブラウザとしての価値が「ウィンドウが 1 つ増える」だけになる

### 案 D: 参照実装（poi）が持つ介入をまとめて許す

- 概要: poi が持っている介入（Cookie の書き込み、ゲーム資材のローカルファイルへの
  差し替え、`window.confirm` と `DMM.netgame.reloadDialog` の置き換え）まで
  含めて、一度に許す
- 却下理由: **個々の是非ではなく、まとめて決めることを却下する。**
  用途も影響範囲も異なるものを 1 つの決定に束ねると、
  必要になったとき「どこまで許されているのか」を誰も言えなくなる。
  必要が生じた用途から順に、個別に判断する

> 参照実装での位置づけ（2026-08-16 時点）:
> poi の Cookie 書き込み（`assets/js/cookie-hack.js`）は**既定で無効の設定項目**であり、
> `poi.misc.dmmcookie` を有効にしたときだけ動く。
> 同じブロックが Accept-Language を `ja-JP` に設定し、
> DMM の海外向けページ（`/foreign/`）へ飛ばされた場合に入口へ戻す処理を持つことから、
> **日本国外からの利用を想定した機能**だと読める
> （`TODO(要検証)`: コードからの推測であり、poi の文書で裏を取っていない）。
> 既定で動くのは CSS 注入（`page-align.js`）と XHR の観測（`xhr-hack.js`）である。

## 決め手

**課金導線を壊さないことを構成の条件に置いたため、入口ページを丸ごと読む以外に道が無くなり、
その代償としてページ構造への依存を受け入れた。**

線を「何を変えるか」の段階に置いたのは、**未知の介入もその場で段に割り当てられ、
どの制約を見て判断すればよいかが決まる**ためである。禁止事項を列挙する形にすると、
列挙されていない介入の扱いが決まらず、逆に列挙されたものは
再検討の余地が無いように読めてしまう。

## 影響

- 実装への影響:
  - 注入スクリプトに「表示のための CSS を当てる」責務が加わる。
    観測（読み取り）と表示調整（書き込み）が同じ経路に同居するため、
    ファイルを分けて責務を分離する
  - 配信元ページの構造が変わると表示が崩れる。
    [external/game-screen.md](../spec/external/game-screen.md) の E-03
    （ゲーム画面の位置を特定できない）が現実的な縮退経路になる
- ドキュメントへの影響:
  - `docs/spec/architecture.md` の「ゲームのページに副作用を与えない」を、
    許す範囲と許さない範囲を明示した記述に置き換える（**人間の承認が必要**）
  - `docs/spec/constraints.md` の C-02 は変更しない。通信は引き続き読み取り専用である
- 取り消す場合のコスト: 低い。注入する CSS を外せば元に戻る。
  ただし取り消すと「ゲーム画面だけを表示する」外部仕様も同時に取り下げることになる
