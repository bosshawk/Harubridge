# ADR-0015: ドキュメント構成を確定する（ADR-0002 / 0006 / 0007 / 0009 / 0010 / 0012 を統合）

- ステータス: Accepted（`docs/kancolle/` の追加は [ADR-0020](0020-kancolle-reference.md) による）
- 日付: 2026-08-02
- 決定者: プロジェクトオーナー
- 統合対象: [ADR-0002](archive/0002-documentation-structure.md), [ADR-0006](archive/0006-split-external-and-internal-spec.md),
  [ADR-0007](archive/0007-observability-based-spec-boundary.md), [ADR-0009](archive/0009-notes-as-github-issues.md),
  [ADR-0010](archive/0010-top-level-doc-layout.md), [ADR-0012](archive/0012-local-notes-directory.md)
- 関連: [ADR-0008](0008-code-as-source-of-truth.md)（何を書かないかの原則。**引き続き有効**）

## 背景と課題

ドキュメント構成は 2 日間で 6 本の ADR を経て現在の形になった。
`3 層構造 → external/internal/guidelines へ分割 → 判断基準の差し替え →
internal/ の廃止 → guidelines の再配置 → notes の廃止と復活`。

このうち `ADR-0009`（`docs/notes/` 廃止）と `ADR-0012`（同ディレクトリの復活）は
**同じ日に決めて同じ日に覆している**。これは意思決定の記録ではなく、検討の途中経過である。

結果として、「いまドキュメントはどう構成されているか」を知るには
ADR を 6 本追い、`Accepted（〜のみ Superseded by 〜）` という但し書きを
解読する必要がある。同じ内容は [docs/README.md](../README.md) に 10 行で書かれている。
**この論点については ADR が理解を助けるどころか妨げている。**

放置すると、将来のエージェントが `ADR-0006` を読んで `docs/spec/internal/` を作り直す。

## 決定

構成に関する上記 6 本を**本 ADR に統合し、すべて `Superseded by ADR-0015` とする。**
以下が現在の構成であり、これが唯一の記録である。

### 配置

```
CLAUDE.md         エージェントが従う規約（自動で読まれる）
CONTRIBUTING.md   進め方・役割分担・依頼の書き方（人が読む）
docs/
├── adr/          なぜそう決めたか
├── spec/         何を作るか（要求層 + architecture.md + external/）
├── guidelines/   どう書くか（横断規約）
└── notes/        手元の書き捨てメモ（**git 管理外**。README.md のみ追跡）
```

**機能ごとの内部仕様は存在しない。コードが正**
（[ADR-0008](0008-code-as-source-of-truth.md)）。

### 何をどこに置くか

| 内容 | 置き場所 |
| --- | --- |
| 決定と却下案 | `docs/adr/` |
| 要求・基本設計・外部仕様 | `docs/spec/` |
| 横断規約 | `docs/guidelines/` |
| 実装の詳細 | **コード**（文書化しない） |
| 他人が読む必要のある検討・論点 | **GitHub Issue** |
| 他人が読む必要のない書き捨てメモ | `docs/notes/`（共有されない） |

Issue と `docs/notes/` の分岐は **「他人（将来の自分を含む）が読む必要があるか」**
の 1 点で判断する。迷ったら Issue。

### 文書とコードの境界

**判断基準の記述は [docs/spec/README.md](../spec/README.md#文書とコードの境界) の 1 箇所のみを正とする。**
他の文書は再掲せずリンクする。要点のみ:

> **「この記述に反する実装をユーザーが使ったとき、
> 画面・操作・通知・設定・保存物のどれかで違いに気づくか？」**
> 気づくなら `external/`、気づかないならコード（骨格のみ `architecture.md`）。

「実装を書き直しても変わらないか」という旧基準は使わない。
実行形態（専用ウィンドウかタブか、OS 通知かアプリ内通知か）は
実装の書き換えで変わりうるが**ユーザーに見えるため外部仕様**であり、
旧基準はここで逆の答えを出す。

### 変更時の承認境界

| 場所 | 変更するとき |
| --- | --- |
| `docs/spec/` 全般 / `docs/guidelines/` | **人間の承認が必要** |
| コード | 外部仕様と基本設計を変えない限り、エージェントの判断で書いてよい |

ただし**相互リンクの追記と一覧表の同期は承認不要**。ここで作業を止めない。

## 検討した選択肢

実際に比較したのは次の 2 つ（[ADR を書く基準](README.md#adr-にする条件) に従い、
検討していない案は記載しない）。

### 案 A: 今後の運用だけ変え、過去の 6 本はそのまま残す

- 利点: 追加作業ゼロ。履歴が完全な形で残る。
- 却下理由: 現在の構成を知るのに 6 本を追う必要が残り、
  将来のエージェントが古い構成を実装し直すリスクが消えない。

### 案 B: 6 本を 1 本に統合する（採用）

- 利点: 現在の構成が 1 箇所で読める。旧 ADR は履歴として残り、失われない。
- 欠点: 「ADR を減らすために ADR を書く」形になる。

## 決め手

**履歴の粒度を捨てて、現在の状態の可読性を取った。**
統合対象の本文は削除しないため、経緯を追いたい場合は各 ADR を読める。

なお**この統合は 1 回限りとする。** 統合の統合を始めると際限がない。
再発は ADR の起票基準を厳しくすること（[adr/README.md](README.md#adr-にする条件)）で防ぐ。

## 影響

- 統合対象 6 本のステータスを `Superseded by ADR-0015` に変更する（本文は変更しない）。
- 他の文書から統合対象への参照を本 ADR に張り替える。
- 取り消す場合のコスト: 低。
