# ADR-0007: 外部仕様と内部仕様の切り分けを可観測性で判断する

- ステータス: Accepted
- 日付: 2026-08-02
- 決定者: プロジェクトオーナー
- 関連: [ADR-0006](0006-split-external-and-internal-spec.md)（本 ADR は 0006 を置き換えず、判断基準を差し替える）

## 背景と課題

[ADR-0006](0006-split-external-and-internal-spec.md) で `docs/spec/` を
external / internal / guidelines に分割し、承認境界をディレクトリに対応づけた。
その際の切り分け基準として
**「実装を全部書き直しても、この記述は変わらないか？ 変わらないなら外部仕様」**
という一文を各所に置いた。

この基準を実際の要求に当てて検証したところ、**中核の要求で逆の答えを出す**ことが判明した。

- **FR-001**「ゲーム画面を単独のウィンドウ／ビューとして表示する」
  実装をデスクトップアプリからブラウザ拡張に書き直せば、この記述は「タブ／サイドパネル」に変わる。
  基準に従えば内部仕様になるが、これ以上なくユーザーに見える記述である。
  FR-005（ウィンドウ位置の復元）、FR-020（OS 通知かアプリ内通知か）も同型。
- 逆方向として、データの保存**形式**は互換維持のため書き換え後も残りやすく、
  基準に従えば外部仕様になるが、ユーザーには見分けられない。

原因は、この基準が **「実装不変 ＝ ユーザー可視」という等式を暗黙に仮定**していることにある。
本プロジェクトでは**実行形態そのものがユーザーに見える**ため、この等式が成立しない。

放置すると、ユーザー可視の振る舞いが `internal/` に分類され、
エージェントが**無承認で変更できてしまう**。ADR-0006 が作った承認境界に穴が開く。

## 決定

切り分けの判断基準を、実装の可変性ではなく**ユーザーからの可観測性**に置き換える。

> **「この記述に反する実装をユーザーが使ったとき、
> 画面・操作・通知・設定・保存物のどれかで違いに気づくか？」**
> 気づくなら外部仕様、気づかないなら内部仕様。

あわせて以下を定める。

1. **判断基準の記述は [docs/spec/README.md](../spec/README.md) の 1 箇所のみを正とする。**
   旧基準は 4 箇所に複製されており、「同じ事実を 2 箇所に書かない」という
   自らのルールに反していた。他の文書はリンクで参照する。
2. **`internal/` のファイルは必須としない。** 永続化する / 観測データに依存する /
   複数機能から使われる共通処理を持つ、のいずれかに該当する場合のみ作成する。
   小さな機能に空疎な 2 ファイル目を強制しない。
3. **外部仕様の異常時の挙動に `E-nn` の ID を振り、内部仕様はそれを参照する。**
   状況の定義とユーザーに見える結果は外部仕様を正とし、内部仕様は検知方法と
   内部処理だけを書く。

## 検討した選択肢

### 案 A: 可観測性ベースの基準に差し替える（採用）

- 利点: 承認境界の目的（ユーザー可視の変更に人間の承認を要求する）と基準が直結する。
  実行形態が変わっても判断がぶれない。
- 欠点: 「気づくか」の判定に幅がある（保存物をユーザーが開いて見るか、など）。
  境界例を注記で個別に潰す必要がある。

### 案 B: 旧基準を維持し、例外リストで穴を塞ぐ

- 概要: 「ただし実行形態は外部仕様とする」などの例外を積む。
- 却下理由: 基準そのものが誤っているため、例外が際限なく増える。
  例外表を読まないエージェントは誤分類し続ける。

### 案 C: 両方の基準を併記し、食い違ったら人間に確認させる

- 却下理由: 判断を止める設計であり、エージェント駆動の利点を殺す。
  食い違いは頻出するため、確認要求が常態化する。

## 決め手

**判断の一貫性を得るために、基準の簡潔さを捨てた。**
旧基準は一文で覚えやすかったが、覚えやすさは誤った分類を防がない。

## 影響

- ドキュメントへの影響:
  - [docs/spec/README.md](../spec/README.md) に新基準と境界例の注記を置く（唯一の正）。
  - `docs/README.md` / `docs/spec/external/README.md` / `.claude/skills/write-spec/SKILL.md`
    の複製をリンクに置き換える。
  - 外部仕様・内部仕様のテンプレートを `E-nn` 参照方式に改める。
- 実装への影響: なし（実装は未着手）。
- 取り消す場合のコスト: 低。仕様ファイルはまだ 1 つも書かれていないため、
  既存文書の再分類は発生しない。
