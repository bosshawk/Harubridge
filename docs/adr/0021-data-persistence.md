## 背景と課題

[ADR-0018](0018-dependencies.md) で永続化に `rusqlite` を選んだが、
**「何を、どういう形で、どこに置くか」は未決**である。
[architecture.md](../spec/architecture.md) の「データの持ち方」は `TODO(未確定)` のまま、
実装に着手できない状態にある。

決めなければならないのは次の 5 点である。

1. 何を永続化し、何をメモリに留めるか
2. マスタデータ（`api_start2/getData`）の扱い
3. 母港へ戻るたびに全量届く `api_port/port` の扱い
4. スキーマのマイグレーション方針
5. 保存場所

### 量の実測

| 対象 | サイズ | 頻度 |
| --- | --- | --- |
| `/kcsapi/api_start2/getData` | **2,332,462 bytes** | ログインのたびに毎回 |
| `/kcsapi/api_port/port` | **271,824 bytes** | 母港に戻るたび。**実測で 1 セッション中 7 回** |

> 出典: サイズは [ADR-0016](0016-tech-stack.md) の検証 3（2026-08-02、オーナー環境の実測）。
> 受信回数は同日・同環境の実測。

受信したものをそのまま貯めると、`api_port/port` だけで **1 セッションあたり約 1.9MB**、
マスタを毎回保存すれば **1 ログインあたり 2.3MB** が積み上がる。
毎日 1 セッション遊ぶだけで年間 1GB に迫る。**素朴な全量保存は最初から成立しない。**

### 二つの緊張

- **C-03（非公開仕様への依存）**: ゲームの仕様は予告なく変わる。
  列を固定したスキーマは、変更のたびに壊れるか、移行を強いられる。
  一方で JSON をそのまま突っ込むと、FR-042（資源の推移）や FR-045（戦果）の集計が書きにくい。
- **C-04 / C-07（データを外に出さない / リポジトリは公開されている）**:
  観測データには提督名・会員 ID・サーバ・トークンが混じりうる。
  生の観測データをそのまま保存すると、エクスポート（FR-046）や不具合報告の添付で
  それが外へ出る経路ができてしまう。

### 既存ツールの実装（調査）

推測を避けるため、公開されている実装を読んだ。

| ツール | 保存の形 | 根拠 |
| --- | --- | --- |
| **航海日誌 (logbook-kai)** | **DB を使わない。** 設定は `./config` に Bean ごとの JSON（Jackson、`FAIL_ON_UNKNOWN_PROPERTIES=false`）。集計用のログは設定で指定したディレクトリに追記 CSV。戦闘ログは `yyyy-MM` ディレクトリに gzip で分割保存し、古いものを削除 | [`Config.java`](https://github.com/sanaehirotaka/logbook-kai/blob/master/src/main/java/logbook/internal/Config.java) / [`log/LogWriter.java`](https://github.com/sanaehirotaka/logbook-kai/blob/master/src/main/java/logbook/internal/log/LogWriter.java) / [`BattleLogs.java`](https://github.com/sanaehirotaka/logbook-kai/blob/master/src/main/java/logbook/internal/BattleLogs.java)。`pom.xml` に DB ドライバの依存が無い |
| **KancolleSniffer** | **DB を使わない。** 設定は `config.xml`。「資材ログ」「戦果」「遠征報告書」「建造報告書」「開発報告書」「改修報告書」をヘッダ行つきの追記 CSV として出力し、出力先を設定で変更できる | [`Config.cs`](https://github.com/fujieda/KancolleSniffer/blob/master/KancolleSniffer/Config.cs) / [`Log/Logger.cs`](https://github.com/fujieda/KancolleSniffer/blob/master/KancolleSniffer/Log/Logger.cs) |

| **KC3改** | **唯一 DB を使う。** Dexie / IndexedDB。戦闘は検索に使う値（出撃 ID・ノード・時刻・評価・ドロップ）を列に出し、戦闘 API の中身は `data` / `yasen` に**塊のまま**入れる。資源は **1 時間に 1 点だけ**記録する。スキーマは `version(n).stores(...)` + `.upgrade()` の連鎖で移行する | [`Database.js`](https://github.com/KC3Kai/KC3Kai/blob/master/src/library/modules/Database.js) / [`objects/Node.js`](https://github.com/KC3Kai/KC3Kai/blob/master/src/library/objects/Node.js) の `buildBattleDBData` / [`managers/PlayerManager.js`](https://github.com/KC3Kai/KC3Kai/blob/master/src/library/managers/PlayerManager.js) の `setResources` |

読み取れた事実は 3 つある。

1. **どのツールも受信レスポンスを全量アーカイブしていない。** 4 本とも、必要な値を抜き出すか、
   意味のある単位まで削ってから保存している。
2. **KC3改 のスキーマは実際に 14 版まで変わっている**（`vr` が 1 → 2 → … → 6.5 → 6.6 → 7 → 7.2 → 73 → 74 → 75 → 76）。
   艦これのツールで固定スキーマを保つのは現実的でない、という実証である。
3. **KC3改 は提督名・サーバ・会員 ID を `account` テーブルに保存している。**
   本プロジェクトは C-04 / C-07 により、ここは踏襲しない。

## 決定

**「状態」は上書き、「事象」は追記**を原則とし、事象は
**「アプリが意味を与えた少数の列」＋「解釈前の JSON 塊」の二層**で SQLite に保存する。
**受信レスポンスの全量は保存せず、保存対象は許可リストで明示的に選ぶ。**
マスタデータは最新 1 世代の抽出済みサブセットのみを持ち、
スキーマは `rusqlite_migration` により `user_version` ベースで**前進のみ**移行する。

### 原則 1: 「状態」は上書き、「事象」は追記

- **状態**（いまの艦隊・艦・装備・入渠・遠征・資源の現在値）は、その時点の値だけが意味を持つ。
  **上書きし、履歴を持たない。**
- **事象**（戦闘の結果、遠征の帰投、建造・開発の結果、資源のサンプル点）は、
  起きたこと自体が記録の対象である。**追記し、更新も削除もしない。**

`api_port/port` は「状態」の塊である。したがって
**1 セッション 7 回の受信をそのまま 7 件保存しない。**
状態の側は最後の 1 件で上書きし、そこから読み取れる事象だけを追記する。

資源（FR-042）は状態と時系列の両方の性格を持つため、
**時刻でバケットを取り、同一バケットには 1 点しか記録しない**。
KC3改 が `floor(サーバ時刻/3600)` を鍵にして 1 時間 1 点としているのと同じ考え方である。
バケット幅そのものは実装の判断とする（コードが正）。

### 原則 2: 受信レスポンスの全量を保存しない。許可リストで選ぶ

> 同じ原則を、解析失敗時のデータとテストデータに適用したものが
> [ADR-0022](0022-observed-data-privacy.md) である。両者は同じ根拠（C-03 により
> フィールドを列挙しきれない）に立つ。片方だけを変えないこと。

保存するのは、**パース層が「記録対象」として明示的に選んだ部分木だけ**である。

- **拒否リスト（提督名やトークンを列挙して落とす）を採らない。**
  C-03 によりフィールドは予告なく増える。増えたフィールドは拒否リストに載っておらず、
  **落とし漏れは静かに起きる。** 許可リストなら、未知のフィールドは既定で保存されない。
- レスポンスの外側の封筒（`api_result` などのメタと、提督情報を含む枝）は最初から通さない。
- **リクエスト URL とパラメータを保存しない。** 認証トークンが乗る経路である。
- **通信ログそのものを保存する機能を作らない。** 必要になった場合は別途 ADR を起こす。

これは NFR-004 / NFR-005 を「保存後に消す」ではなく
**「そもそも入れない」**として構造で満たすための選択である。

### 原則 3: 事象は二層で持つ —— 意味を与えた列と、解釈前の JSON

事象 1 件につき、

1. **アプリが意味を与えた少数の値を列にする。** 集計とインデックスはここだけを使う
2. **残りは、許可リストを通した JSON をそのまま 1 つの列に置く**

**新しい切り口が必要になったとき、テーブルを作り直さずに列を後から生やせる。**
SQLite は生成列を持ち（3.31.0 / 2020-01-22 以降）、
`ALTER TABLE ADD COLUMN` で **VIRTUAL の生成列なら追加できる**
（STORED は追加できない）。JSON 関数は 3.38.0 / 2022-02-22 以降**既定で有効**であり、
`rusqlite` 0.40.1 が同梱する SQLite は **3.53.2** なので、どちらも前提にできる。

出典:
[Generated Columns](https://www.sqlite.org/gencol.html) /
[JSON Functions](https://www.sqlite.org/json1.html) /
[ALTER TABLE](https://www.sqlite.org/lang_altertable.html) /
[rusqlite v0.40.1 リリースノート](https://github.com/rusqlite/rusqlite/releases/tag/v0.40.1)

したがって、ゲームの仕様が変わって「あの値も集計したい」となっても、
**過去の記録を捨てずに解釈をやり直せる。**
KC3改 が戦闘の中身を `data` / `yasen` に塊のまま持ちつつ、
検索に使う値だけを列に出しているのと同じ構えである。

**JSON 塊は「解釈前の形」で置き、アプリの都合で整形し直さない。**
整形してしまうと、整形ロジックのバグが記録そのものを壊す。

### 原則 4: マスタデータは最新 1 世代の抽出済みサブセットだけ

`api_start2/getData`（2.3MB）について:

- **毎回パースする。** 受信は避けられず（C-02）、パースを省く仕掛けを持つ価値が薄い。
  パース結果はメモリに載せ、セッション中はそこを正とする
- **全量を保存しない。** 保存するのは、過去の記録を後から表示するために必要な
  最小限のサブセット（艦・装備・海域・遠征などの識別子と名前）である。
  poi が `api_mst_*` の必要な枝だけを取り出しているのと同じ絞り込みを行う
- **バージョンは受信本文の内容ハッシュで持つ。** 前回と一致するなら書き込みをスキップする。
  ゲーム側にマスタのバージョン番号があるかは未確認であり、
  `TODO(要検証)` として推測に立たない
- **過去世代のマスタを保持しない。** 記録側はマスタ ID を持ち、表示は常に最新のマスタで解釈する。
  世代を持てば「この記録は当時どう見えたか」を再現できるが、
  そのために 2.3MB 級のデータを積み増す価値が現時点で示されていない

### 原則 5: マイグレーションは `rusqlite_migration` で前進のみ

- **`rusqlite_migration` 2.6.0 を採用する**（crates.io の `recent_downloads` 262 万。
  ADR-0018 と同じ指標。2026-08-02 取得）。
  マイグレーションの適用状況を SQLite の `user_version` に持つため、
  履歴テーブルを増やさずに済む
- **down マイグレーションを書かない。** ローカルの記録は巻き戻す相手がいない。
  取り消したいときは、打ち消す前進のマイグレーションを追加する
- **記録は捨てない、解釈をやり直す。** 列の意味が変わったときは、
  JSON 塊から列を作り直すマイグレーションを書く。これが原則 3 を置いた理由である
- 起動時に最新まで適用する。**適用前に DB ファイルの退避コピーを作る。**
  適用に失敗した場合はアプリを止めず、**記録機能だけを無効化して起動する**（NFR-003 の縮退）

### 原則 6: 保存場所はローミングしないアプリ専用ディレクトリ

- Tauri の **`app_local_data_dir()`** 配下に置く。
  macOS は `~/Library/Application Support/<bundle identifier>`、
  Windows は `%LOCALAPPDATA%\<bundle identifier>`
  （[`PathResolver`](https://docs.rs/tauri/latest/tauri/path/struct.PathResolver.html)）
- **Windows でローミング側（`app_data_dir()`）を使わない。**
  数百 MB になりうる DB がプロファイル同期の対象になるため
- **UI から保存先を開く導線を用意する**（NFR-008）。パスを表示するだけにしない
- 設定は記録と分け、`tauri-plugin-store` に任せる（[ADR-0018](0018-dependencies.md)）

### 原則 7: 履歴をメモリに溜めない

過去の記録はメモリに載せず、必要になったときに SQL で引く。
メモリに常駐するのは「いまの状態」とマスタだけとする。
これが NFR-006（長時間起動でメモリが増え続けない）への構造的な答えである。

## 検討した選択肢

### 案 A: 二層（意味を与えた列 ＋ 解釈前の JSON 塊）（採用）

- 概要: 事象ごとに、集計に使う少数の値を列に出し、残りを JSON 列に置く。
  新しい切り口は VIRTUAL 生成列を後から追加して得る
- 利点:
  - 仕様変更で列が足りなくなっても、**過去の記録を捨てずに解釈をやり直せる**
  - 集計は列に対して普通の SQL で書ける
  - テーブル再構築（[ALTER TABLE](https://www.sqlite.org/lang_altertable.html) の 12 ステップ手順）を
    日常的に踏まずに済む
  - KC3改 に同型の前例がある
- 欠点:
  - 同じ値が列と JSON の両方に存在する。**列が正**という規律を守り続ける必要がある
  - JSON 塊のぶんストレージを余分に使う
  - 「どこまで列にするか」の判断が実装のたびに必要になる

### 案 B: 完全に正規化した固定スキーマ

- 概要: レスポンスの構造を素直にテーブルへ写し、すべてを列にする
- 利点: 集計が最も書きやすい。型が効き、容量も最小
- 欠点: 未知のフィールドが来た時点で受け皿がなく、捨てるしかない
- 却下理由: KC3改 が 14 版のスキーマ変更を重ねている事実（`Database.js` の `vr`）が示すとおり、
  この対象で列を固定し続けることは実際にできていない（C-03）

### 案 C: 受信レスポンスをそのままアーカイブする

- 概要: `/kcsapi/` のレスポンスを丸ごと時系列で保存し、集計は後からその上で行う
- 利点: 取りこぼしが原理的に無い。将来どんな集計が欲しくなっても遡れる
- 欠点: 集計のたびに全件を舐める必要があり、SQL の利点が失われる
- 却下理由: 量（マスタ 2.3MB／ログイン、`api_port/port` 271KB × 7／セッション）と、
  提督名・トークンが**除去されないまま**残ることの両方が受け入れられない（C-04 / C-07）

### 案 D: DB を使わず、JSON ＋ CSV のファイル群にする（航海日誌 / KancolleSniffer 方式）

- 概要: 設定を JSON、集計対象を追記 CSV、戦闘の詳細を gzip した JSON ファイルとして置く
- 利点:
  - **2 本の実ツールが長期運用している実績がある**
  - ユーザーが中身をそのまま読める。エクスポート（FR-046）が「コピーするだけ」で済む
  - スキーマという概念が無いため、仕様変更で壊れない
- 却下理由: FR-042（資源の推移）や FR-045（戦果）の集計を自前で書くことになり、
  [ADR-0018](0018-dependencies.md) が `redb` を却下した理由（時系列の集計に SQL が使えない）が
  そのまま当てはまる

### 案 E: マスタデータを世代管理して全量保存する

- 概要: `api_start2/getData` の内容が変わるたびに新しい世代として保存し、
  記録側から「当時のマスタ」を参照できるようにする
- 却下理由: 1 世代 2.3MB を積み増す対価が「過去の記録を当時の名前で表示できる」ことに留まり、
  現時点の要求（E 区分）でそれを必要とするものが無い

### マイグレーション手段の比較

#### 案 A': `rusqlite_migration` 2.6.0（採用）

- 概要: 適用状況を SQLite の `user_version`（ファイル先頭の固定オフセットにある整数）に持つ。
  マイグレーションは Rust のコード中に SQL 文字列として並べ、`to_latest()` で適用する
- 利点: 履歴テーブルを持たない。`rusqlite` に直接載る。`recent_downloads` 262 万
- 欠点: `user_version` は単一の整数であり、分岐した履歴を表現できない
  （前進のみの方針では問題にならない）

出典: [rusqlite_migration](https://github.com/cljoly/rusqlite_migration) /
[crates.io](https://crates.io/crates/rusqlite_migration)

#### 案 B': `refinery` 0.9.2

- 概要: `V{番号}__{名前}.sql` 形式のファイルを `embed_migrations!` で埋め込み、
  適用履歴を専用テーブルに持つ。`rusqlite` を含む複数ドライバに対応する。down は持たない
- 却下理由: 複数 DB への対応が本アプリでは利点にならず、
  `recent_downloads` 187 万と採用規模でも `rusqlite_migration` を下回る

出典: [refinery](https://github.com/rust-db/refinery)

#### 案 C': 自前で `user_version` を見て分岐する

- 概要: 依存を増やさず、起動時に `user_version` を読んで必要な SQL を順に流す
- 却下理由: 適用済み判定とトランザクション境界を自前で持つことになり、
  それは `rusqlite_migration` が既にやっていることそのものである。
  [ADR-0003](0003-agent-driven-development.md) の体制では、
  検証済みの実装を再発明する側にリスクが寄る

## 決め手

**「あとから解釈をやり直せること」を得るために、
「保存した時点で完全に正規化された、集計しやすいスキーマ」を捨てた。**

## 影響

- **実装への影響:**
  - パース層は「表示のための解釈」に加えて、**「保存してよいものを選ぶ許可リスト」**を持つ。
    これは C-03 の局所化境界（[architecture.md](../spec/architecture.md)）の内側に置く
  - `api_port/port` の受信ハンドラは、状態の上書きと事象の追記を分けて扱う
  - `rusqlite_migration` を依存に追加する（[ADR-0018](0018-dependencies.md) の一覧に 1 行増える）
  - 起動時のマイグレーション失敗を「記録機能のみ無効化」として縮退させる経路が必要になる（NFR-003）
- **ドキュメントへの影響:**
  - [architecture.md](../spec/architecture.md) の「データの持ち方」（現在 `TODO(未確定)`）を
    本 ADR の原則で埋める。**未解決事項からも 1 行外れる**
