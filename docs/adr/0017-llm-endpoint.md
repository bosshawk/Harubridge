# ADR-0017: LLM 連携は OpenAI 互換エンドポイント 1 本に絞り、サーバはユーザーが管理する

- ステータス: **Proposed**
- 日付: 2026-08-02
- 決定者: 承認待ち（`Accepted` にする時点で承認者名に書き換える）
- 関連: [ADR-0016](0016-tech-stack.md), [constraints.md](../spec/constraints.md) C-04,
  検討: Issue #4

## 背景と課題

AI 支援機能（[requirements.md](../spec/requirements.md) の G 区分）を実装するにあたり、
当初は「クラウドの LLM に艦隊データを送る」前提で検討し、
[C-04](../spec/constraints.md)（取得したデータを外部に出さない）との衝突を論点としていた（Issue #4）。

しかし**ローカル LLM を使えば外部送信は発生しない。**
前提が変わるため、論点は「C-04 をどう緩めるか」ではなく
**「送信先をどう選べるようにするか」**になる。

あわせて、**LLM サーバを提供側が用意することはできない**（コスト・可用性・責任のいずれも負えない）。
サーバはユーザーが管理する前提で設計する必要がある。

## 決定

**LLM への接続を「OpenAI 互換の `/v1/chat/completions` を叩く」1 本に絞る。**

- アプリが設定として持つのは **エンドポイント URL / モデル名 / API キー（任意）** のみ
- **プロバイダ固有の SDK や実装を持たない**
- **LLM サーバを同梱しない。ユーザーが用意・管理する**
- **AI 機能は既定で無効。** 有効化にはユーザーがエンドポイントを設定する必要がある

これにより、次のすべてが同じ 1 つの実装で扱える。

| 送信先 | 外部送信 | 例 |
| --- | --- | --- |
| ローカル | **発生しない** | Ollama / LM Studio / vLLM |
| ローカルのゲートウェイ | 設定次第 | LiteLLM Proxy（100+ プロバイダを統合） |
| クラウド | 発生する | ユーザーが明示的に指定した場合のみ |

### C-04 との関係

**C-04 は改訂しない。** 現行の条文のままで両立する。

- **既定ではエンドポイントが未設定であり、外部送信は起こらない**
- ローカルを指定した場合、データは端末から出ない
- クラウドを指定するのは**ユーザー自身の明示的な選択**であり、
  C-04 の「ユーザーが明示的に操作したエクスポートのみ許可する」の範囲に収まる

ただし次を実装上の要件とする。

- **送信前に、何を送るかをユーザーが確認できること**
- **提督名・アカウント ID・サーバ番号は送らない**
- **AI 機能を無効にしても、他のすべての機能が完全に動くこと**

## 検討した選択肢

### 案 A: OpenAI 互換エンドポイント 1 本（採用）

- 利点:
  - **実装が 1 つで済む。** LiteLLM Proxy は 100+ プロバイダを単一の
    OpenAI 互換エンドポイントに束ねる。Ollama も OpenAI 互換 API を持つ。
    したがって「切り替え可能にする」ための分岐をアプリ側に持つ必要がない
  - ローカルとクラウドの選択が**ユーザーの設定 1 つ**に還元される
  - 外部依存が「HTTP で JSON を送る」だけになり、局所化できる
- 欠点: プロバイダ固有の機能（特殊なツール呼び出しなど）は使えない

### 案 B: プロバイダごとに SDK を実装する

- 却下理由: 対応プロバイダの数だけ実装とメンテナンスが増える。
  ユーザーが LiteLLM を挟めば案 A で同じことができ、**こちらが持つ理由がない。**

### 案 C: LLM ランタイムをアプリに同梱する（llama.cpp 等）

- 概要: 推論エンジンとモデルをアプリに組み込む
- 却下理由: 配布サイズがモデル込みで数 GB になる。
  [ADR-0016](0016-tech-stack.md) で Chromium 同梱を避けた判断と整合しない。
  モデルの選択・更新もユーザーの環境と好みに依存する。

### 案 D: こちらが LLM サーバを用意して提供する

- 却下理由: **提供側がコスト・可用性・責任を負えない。**
  個人プロジェクト（[overview.md](../spec/overview.md)）の規模を超える。

## 決め手

**プロバイダの多様性への対応を、LiteLLM に外出しした。**
アプリは「OpenAI 互換の口を 1 つ叩く」だけを知っていればよく、
どのモデルをどこで動かすかはユーザーの領域として切り離す。

副次的に、**この構成では C-04 を改訂せずに済む。**
既定で外部送信が発生しないため、制約の根幹に手を入れる必要がなくなった。

## 影響

- [requirements.md](../spec/requirements.md) の G 区分を確定できる（エンドポイント設定の要求を追加）
- [architecture.md](../spec/architecture.md) に、LLM 連携が
  「OpenAI 互換 HTTP 1 本」に閉じることを記述する
- 外部依存が 1 つ増える（HTTP クライアント）。プロバイダ SDK は増えない
- 取り消す場合のコスト: 低（設定項目と HTTP 呼び出しのみ）
