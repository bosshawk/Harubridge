# ADR-0002: ドキュメントを notes / spec / adr の 3 層で管理する

- ステータス: Accepted
- 日付: 2026-08-01
- 決定者: プロジェクトオーナー
- 関連: [ADR-0001](0001-record-architecture-decisions.md), [docs/README.md](../README.md)

## 背景と課題

実装前の段階で、扱う文書には性質の異なるものが混在する。

- まだ決まっていない調査メモ・思いつき
- 決まった仕様
- 決定に至った理由

これらを 1 つの `docs/` にまとめて置くと、
「この記述は確定事項なのか、検討中の案なのか」が読み手（特にエージェント）に判別できない。
未確定のメモを仕様と誤読して実装されるのが最も危険な失敗である。

## 決定

ドキュメントを**変化の速さ**で 3 層に分割し、置き場所そのものが
「その記述の確度」を表すようにする。

| 層 | 場所 | 意味 | 更新の仕方 |
| --- | --- | --- | --- |
| 暫定 | `docs/notes/` | まだ決まっていない | 自由・破棄前提 |
| 仕様 | `docs/spec/` | いまの正解 | 上書き |
| 決定 | `docs/adr/` | なぜそう決めたか | 追記のみ・不変 |

加えて、手順書を `docs/guides/` に置く。
notes に書かれた内容は、確定した時点で spec または adr へ**昇格**させ、
元のメモは `docs/notes/archive/` に移す。

運用の詳細は [docs/README.md](../README.md) に記述する。

## 検討した選択肢

### 案 A: notes / spec / adr の 3 層（採用）

- 概要: 上記のとおり。
- 利点: ディレクトリを見るだけで確度が分かる。エージェントに
  「spec と関連 ADR だけ読め」と指示でき、未確定情報の混入を防げる。
- 欠点: 昇格作業という運用コストが発生する。放置すると notes が墓場になる。

### 案 B: `docs/` フラット構成 + 各文書の冒頭にステータス記載

- 概要: 1 階層にすべて置き、ファイル先頭で `status: draft` などを宣言する。
- 利点: 移動が不要で運用が軽い。
- 欠点: ステータスの書き忘れが即事故になる。
  「ディレクトリを指定して読ませる」ができず、文脈の切り出しが雑になる。
- 却下理由: 安全側の既定値が無い構成であるため。

### 案 C: Wiki / 外部ツール（Notion など）で管理

- 概要: ドキュメントをリポジトリ外に置く。
- 利点: 編集体験が良い。図が扱いやすい。
- 却下理由: エージェントがローカルから直接読めない。
  コードとドキュメントのバージョンが乖離する。

## 決め手

「未確定の記述を確定仕様として実装される」事故を、
**運用ルールではなくディレクトリ構造で防げる**ことを最優先した。

## 影響

- ドキュメントへの影響: `docs/{spec,adr,notes,guides}` を新設。
- 運用への影響: notes の昇格・棚卸しが定期作業として発生する。
  点検は `.claude/skills/docs-audit` で半自動化する。
- 取り消す場合のコスト: 低（ファイル移動のみ）。

## 未解決事項

- notes の棚卸し頻度は「1 か月放置で見直し」を暫定とする。運用しながら調整する。
