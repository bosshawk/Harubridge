# ADR-0016: 技術構成に Electron + TypeScript + React を採用する

- ステータス: **Proposed**
- 日付: 2026-08-02
- 決定者: 承認待ち（`Accepted` にする時点で承認者名に書き換える）
- 関連: [ADR-0004](0004-defer-tech-stack-decision.md)（本 ADR が採択されれば置き換える）,
  [ADR-0003](0003-agent-driven-development.md), [ADR-0011](0011-license-mit.md),
  調査: Issue #1 / #2

## 背景と課題

オーナーから技術選定を進める指示があり、あわせて要件が示された。

1. **最低限 macOS で動作すること。Windows でも動作すること**
2. **ローカルの処理性能を重視する**（Rust / Go も検討対象に含める）
3. React などの Web 系も比較対象に含める

前提として、本アプリの中核は `/kcsapi/` の**レスポンス本文を観測**して可視化することであり
（Issue #1）、この一点で選択肢が絞られる。

> **注意**: [ADR-0004](0004-defer-tech-stack-decision.md) は「要求が固まるまで技術構成を決めない」と定めており、
> 要求は現在 TBD である。本 ADR はその判断を覆すものであり、**要求次第で手戻りが生じうる**。
> ただし後述のとおり、macOS 対応という要件だけで観測方式がほぼ一意に決まるため、
> 手戻りの範囲は限定的と見る。

## 決定

以下を採用する。

| レイヤ | 採用 |
| --- | --- |
| ブラウザランタイム | **Electron**（Chromium 同梱） |
| 観測方式 | **アプリ内プロキシ**（自前 CA を**同梱ブラウザにのみ**信頼させる） |
| コア言語 | **TypeScript** |
| UI | **React** |

**OS の信頼ストアには一切触れない。** ユーザーに CA 証明書のインストールを求めない。

## なぜこの構成になるか

### 1. macOS 必須が、Chromium 同梱をほぼ強制する

レスポンス本文を取得する正式な API の有無（Issue #2 のコメント参照）:

| ランタイム | 本文取得 |
| --- | --- |
| CEF / Electron（Chromium 同梱） | あり |
| WebView2（Windows のみ） | あり |
| **WKWebView（macOS）** | **無い**。`WKURLSchemeHandler` は http/https 不可 |

→ **macOS を含む以上、OS の WebView に頼る構成（Tauri / wry など）は成立しない。**
FUSOU が Tauri でありながらプロキシ方式かつ macOS 非対応であることが、この制約を裏づけている。

### 2. 「同梱ブラウザに自前 CA を信頼させる」が MITM の欠点を消す

[Issue #2](../../issues/2) では MITM 方式の欠点を「ユーザーに CA 証明書のインストールを強いる」とした。
しかし**ブラウザを同梱する場合、信頼させる相手は自分のブラウザだけでよい。**

- OS の信頼ストアを汚さない。他のアプリの TLS 通信に影響しない
- 復号できるのは自アプリ内のセッションのみ
- プロキシとして受けるため**本文取得が確実**。CDP（`webContents.debugger`）の
  既知の不具合（`No resource with given identifier found` 等）を回避できる

poi が `lib/proxy.ts` と `game-api-broadcaster.ts` を持つ構成であることから、
同型の設計と推測される（`TODO(要検証)`: 実装未読）。

### 3. 性能要件について（重要な訂正）

**Rust / Go を採っても、支配的なコストは変わらない。**

本アプリの計算コストの大半は **Chromium によるゲーム画面の描画**であり、
これはどの言語を選んでも同じ Chromium が担う。
観測処理は 1 リクエストあたり数十 KB の JSON パースと集計であり、
TypeScript で処理して体感差が出る規模ではない（`TODO(要検証)`: 実測していない）。

差が出うるのは常駐メモリ・起動時間・大量の履歴データ集計だが、
**それらは「Chromium を抱える」時点で決まる部分が大きい。**
性能のためだけに Rust / Go を選ぶ根拠は薄い。

## 検討した選択肢

### 案 A: Electron + TypeScript + React（採用）

- 利点:
  - **poi が同一構成で長期運用されている実績**（Electron + React + Redux + TypeScript, MIT）。
    艦これという対象に対して構成が成立することが実証済み
  - 情報量が最も多く型もあるため、**実装をすべてエージェントが行う体制
    （[ADR-0003](0003-agent-driven-development.md)）に最も適合する**
  - Windows / macOS / Linux で同一コード
- 欠点:
  - 配布サイズが大きい（Chromium 同梱）
  - Electron 自体の更新追従が必要

### 案 B: Go + CEF（Energy フレームワーク）

- 概要: Energy は CEF を組み込んだ Go 製のクロスプラットフォーム GUI フレームワーク。
  Windows / macOS / Linux 対応。フロントエンドに Vue / React 等を使える
- 利点:
  - CEF の `GetResourceResponseFilter` は API 仕様上
    **request / response を変更できない**と規定されており、
    [C-02](../spec/constraints.md)（読み取り専用）を API の性質として担保できる
  - 単一バイナリに近い配布、ネイティブの処理性能
- 却下理由:
  - 日本語・英語圏の情報量が Electron に比べて少なく、**エージェントが参照できる前例が薄い**。
    [ADR-0003](0003-agent-driven-development.md) の体制ではこれが直接リスクになる
  - 艦これ界隈での採用実績が確認できず、未知の障害を自力で解く必要がある
  - 性能上の利得が、上述のとおり支配的コストに効かない

### 案 C: Rust + CEF

- 却下理由: **Rust の CEF バインディングが断片化しており、
  広く採用された本命クレートが存在しない。** 複数プロジェクトが並立し、
  「積極的にサポートしない」「多くが未実装で十分にテストされていない」と
  作者自身が明記しているものが複数ある。
  エージェントが実装する前提で、この土台は選べない。

### 案 D: Rust / Go + Tauri（または wry）

- 却下理由: OS の WebView を使うため **macOS でレスポンス本文が取得できない**（上述）。
  要件 1 を満たせない。プロキシで迂回すると OS 信頼ストアへの CA 導入が必要になり、
  案 A の利点を失う。

### 案 E: ブラウザ拡張 + ローカル中継（logbook-kai-messageflow 方式）

- 却下理由: `chrome.devtools.network` は **DevTools を開いていないと発火しない**（Issue #2）。
  常用する専ブラの体験として成立しない。加えて Manifest V3 移行で KC3改 が動作不能になった前例があり、
  **ブラウザベンダーの都合で一方的に壊れる位置**にある。

### 案 F: Electron + Rust / Go サイドカー（ハイブリッド）

- 概要: UI とブラウザは Electron、観測・永続化を Rust / Go の別プロセスに分離する
- 却下理由: プロセス間通信とビルドパイプラインが二重になり、複雑性が跳ね上がる。
  **その複雑性に見合う性能上の必要が現時点で示されていない。**
  将来ボトルネックが実測で判明した場合に、この案を再検討する余地は残る。

## 決め手

**エージェントが実装できることを、実行性能より優先した。**

[ADR-0003](0003-agent-driven-development.md) によりコードはすべてエージェントが書く。
その体制では「前例と情報量」が実装可能性そのものを左右する。
Rust / Go の性能上の利得は、Chromium が支配的コストである本アプリでは限定的であり、
バインディングの未成熟さ・前例の薄さというリスクに見合わない。
