## 前提: ゲームは回数を返さない

`api_get_member/questlist` が返すのは次の 2 つだけで、「3/5」のような回数は存在しない。

| フィールド | 値 |
| --- | --- |
| `api_state` | 1 = 未受領 / 2 = 遂行中 / 3 = 達成 |
| `api_progress_flag` | 0 / 1 = 50% 以上 / 2 = 80% 以上 |

詳細は [api_get_member_questlist.md](../api/api_get_member_questlist.md)。

したがって**回数は自前で数える**（FR-050。オーナー判断 2026-08-02）。

## 逆算モデル

自前カウンタと `api_progress_flag` が矛盾したとき、フラグから回数の下限を逆算して補正する。
**この逆算の仕方が実装ごとに割れている。**

max = 3 の任務で `api_progress_flag = 1`（50% 以上）だったときの解釈:

| 実装 | 結果 | モデル |
| --- | --- | --- |
| 七四式電子観測儀 | 2/3 | 「50% でまだ 2/3」の任務を例外リスト（19 件）で持つ |
| KC3改 | 1/3 | max = 3 の特例リストで持つ |
| KancolleSniffer | 1/3 | 「Max = 3 なら Shift = 2」の一般則 + 任務ごとの上書き |

**どれが正しいかは外から見分けられない。** ゲーム内部の閾値が観測できないため。

### 採用するモデル

**KancolleSniffer 方式（一般則 + 任務ごとの上書き）を採る。**

- 既定は式で決まり、**例外だけをデータで持つ**ため、テーブルが小さくなる
- 未登録の任務にも既定値が効く（縮退できる）

`data/kancolle/quests.json` の `shift` がその上書きにあたる。

## 注意すべきクセ

素朴な加算では合わない事例が知られている。

- **共有カウンタ** —— デイリーの開発・建造など、複数の任務が同じ回数を共有する
- **1/5 から始まる任務** —— 受注時点で内部進捗が 0 でないものがある
- **`api_state` が 2 のまま達成扱いになる任務** —— クライアント側で判定される
  （`kcmemo.md` が 20 件列挙）

## テーブルの保守

任務は**ゲーム更新のたびに追加される**。既存実装が持つ定義数は
KC3改 135 件、KancolleSniffer 186 件、七四式は約 506 箇所。

**最初から全件を揃えない。** よく使う任務から埋め、
**未登録の任務は「進捗を数えない」と表示して縮退する**（FR-050 の段階的実装）。
