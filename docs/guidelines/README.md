# ガイドライン

**個別の機能に属さない横断ルール**を書く場所。コーディング規約・エラー処理方針・
ログ方針・テスト方針・UI 原則など。

> **この階層の変更には人間の承認が必要**。
> 影響がリポジトリ全体に及ぶため。

## 仕様との違い

| | 仕様（[`docs/spec/`](../spec)） | ガイドライン |
| --- | --- | --- |
| 対象 | 特定の機能 | 全コードに横断的 |
| 問い | 「この機能は何をするか」 | 「どう書くか」 |
| 寿命 | 機能が消えれば消える | プロジェクトと同じ |
| 例 | 遠征タイマーは残り時間を分単位で表示する | 時刻は必ず単調増加時計から取得する |

仕様とは別の軸なので、`spec/` の下ではなく並列に置く。
開発の**進め方**は [CONTRIBUTING.md](../../CONTRIBUTING.md)。

## 実装しながら見直す

**運用中のガイドラインは確定版ではない。**
実装を 1 行も書かないうちに定めたものであり、
**実際に書いてみて初めて、無理があるルールと足りないルールが分かる。**

したがって次のように扱う。

1. **ルールに合わない実装が要ると分かったら、コード側で例外を作らない。**
   `#[allow(...)]` や `eslint-disable` で黙って逃げるのではなく、
   **ガイドラインを直す提案を出す**（変更には人間の承認が要る）。
   例外が積み上がった規約は、守られていないのに守られているように見えるため最も危険である
2. **実装初期は変更が頻繁に起きる前提で運用する。**
   ルールの追加・削除・強度（`MUST` / `SHOULD` / `MAY`）の変更を、
   規約の失敗ではなく想定どおりの経過として扱う
3. **削除の候補を意識する。** 実装で一度も適用されなかったルールと、
   繰り返し破ることになったルールは、どちらも見直しの対象である。
   **数を増やすことは目的ではない**
4. ただし**検査を弱める方向の変更は別枠**とする。
   `any` / `as` / `unwrap` の許容範囲を広げる変更は、
   人間が常時レビューしない体制では防波堤そのものを下げることになるため、
   「実装しながらの見直し」に含めず、個別に判断する

## 書き方

- [`_template.md`](_template.md) を `<名前>.md` にコピーして書く。
- ルールには強度（`MUST` / `SHOULD` / `MAY`）と ID（`G-nn-mm`）を付ける。
  エージェントへの指摘やレビューで ID 参照できるようにするため。
- **良い例と悪い例を必ず並べる。** 抽象的なルールだけでは守られない。
- 「なぜそうするか」を書く。理由の無いルールは、状況が変わったときに判断できない。
