# 要求仕様

> ステータス: **承認済み**（2026-08-02、プロジェクトオーナー）
>
> 既存ツールの機能調査（Issue #3）をもとに起こした一覧。
> **順次実装する前提で、優先度と実装状況をこの表で管理する。**
>
> G（AI 支援）の LLM 連携は OpenAI 互換エンドポイント 1 本に絞る。

## 記法

- ID は `FR-nnn`（機能要求）/ `NFR-nnn`（非機能要求）。
  **一度振った ID は再利用しない**（削除した要求の ID は欠番のまま残す）。
- 優先度: `Must`（無いと成立しない）/ `Should`（あるべき）/ `Could`（あれば良い）
- 状態: `未着手` / `実装中` / `実装済` / `対象外`
- 実装依頼・外部仕様・テストは、この ID を使って要求を参照する。
- **状態の更新に承認は不要**（実装の進捗を反映する機械的な同期作業として扱う）。

## 方針

**統合型**を目指す。ゲーム画面の表示と情報の可視化を 1 つのアプリで完結させる
（Issue #3 の分類による）。計算系（D）も対象に含める。

## F. 任務

> **進捗は自前で数える**（オーナー判断、2026-08-02）。
> ゲームは段階（50% / 80% 以上）しか返さないため
> （[questlist の記録](../kancolle/api/api_get_member_questlist.md)）、
> 「ゲームが返す段階だけを表示する」縮小案は採らない。
>
> これにより**任務ごとの達成条件の知識**と、
> **事象を数えて保持する仕組み**（永続化イベントからの導出状態）が必要になる。

## G. AI 支援

> **LLM サーバは同梱せず、ユーザーが用意・管理する。**
> アプリは **OpenAI 互換の `/v1/chat/completions` を叩くだけ**とし、
> 送信先はユーザーが設定する。
> ローカル（Ollama など）を指定すれば**外部送信は発生しない**ため、
> [C-04](constraints.md) を改訂せずに両立する。
>
> **AI 機能は既定で無効。** 無効でも他のすべての機能が動くこと。

| ID | 要求 | 優先度 | 状態 |
