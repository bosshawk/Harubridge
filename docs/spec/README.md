# 仕様書 (spec)

**コードから読み取れないものだけ**を書く場所（[ADR-0008](../adr/0008-code-as-source-of-truth.md)）。

## 構成

```
docs/spec/
├── overview.md / requirements.md / constraints.md / glossary.md   要求層: 何が必要か
├── architecture.md   基本設計: 機能をまたいで効く構造      ← 維持・メンテする
└── external/         外部仕様: ユーザーへの約束と受け入れ条件 ← 最小限に保つ
```

横断規約は仕様ではないため [`docs/guidelines/`](../guidelines/) に並列で置く
（[ADR-0010](../adr/0010-top-level-doc-layout.md)）。

**機能ごとの内部仕様は存在しない。コードが正。**
その場の方針・検討メモは GitHub Issue に置く（[ADR-0009](../adr/0009-notes-as-github-issues.md)）。

| ファイル / ディレクトリ | 内容 | 変更するとき |
| --- | --- | --- |
| [`overview.md`](overview.md) | 何を作るか、スコープと非スコープ | **人間の承認が必要** |
| [`constraints.md`](constraints.md) | 前提と制約。**実装前に必ず読む** | **人間の承認が必要** |
| [`requirements.md`](requirements.md) | 機能要求 (FR) / 非機能要求 (NFR) | **人間の承認が必要** |
| [`glossary.md`](glossary.md) | 用語集 | 承認不要 |
| [`architecture.md`](architecture.md) | 基本設計。全体構造・データの持ち方・外部との接点 | 構造を変える変更は**承認が必要** |
| [`external/`](external/) | 画面・操作・表示・設定・通知 | **人間の承認が必要** |

`architecture.md` と [`../guidelines/`](../guidelines/) は、技術構成が決まるまで骨子のみ
（[ADR-0004](../adr/0004-defer-tech-stack-decision.md)）。

## 文書とコードの境界

> **この節がこの判断基準の唯一の正。** 他の文書は基準を再掲せず、ここへリンクすること。

### 第 1 の問い: ユーザーに見えるか

> **「この記述に反する実装をユーザーが使ったとき、
> 画面・操作・通知・設定・保存物のどれかで違いに気づくか？」**

気づくなら [`external/`](external/) に書く。気づかないなら第 2 の問いへ。

境界例（直感に反するため、記憶に頼らず毎回参照する）:

- **実行形態はユーザーに見える。** 専用ウィンドウかタブか、OS 通知かアプリ内通知かは
  実装の書き換えで変わりうるが、**外部仕様**である。
  実行形態を変える書き換えは実装変更ではなく仕様変更であり、承認が必要。
- データ・設定の保存**形式**はユーザーが見分けられないため**コード**に委ねる。
  ただし保存**場所**はユーザーが辿れるため、外部仕様に書く。
- 性能目標の**数値**は体感できるため外部仕様、それを達成する**手段**はコードに委ねる。

### 第 2 の問い: 古くなったとき害があるか

> **「その記述が実装とずれたとき、読んだ人が誤った前提を持つか？」**

- **持つ、かつ機能をまたいで効く** → [`architecture.md`](architecture.md)（基本設計）
- **持つ、かつ書き方の規約である** → [`../guidelines/`](../guidelines/)
- **それ以外** → **書かない。コードが正。**

処理フロー・クラス構成・データ構造・個別 API のパースは書かない。
コードを読めば分かるものを文書化すると二重管理になり、必ず片方が古くなる。
**古い文書は無い文書より悪い**（[ADR-0008](../adr/0008-code-as-source-of-truth.md)）。

### なぜそうしたか、は ADR へ

`architecture.md` は「いまどういう構造か」を現在形で書く。
「なぜその構造にしたか」は [ADR](../adr/) が担当する。

## 読む順番

1. [`overview.md`](overview.md) — 何を作るか
2. [`constraints.md`](constraints.md) — 越えてはならない制約
3. [`requirements.md`](requirements.md) — 要求一覧
4. [`architecture.md`](architecture.md) — 全体構造
5. [`external/`](external/) — 対象機能の外部仕様
6. [`../guidelines/`](../guidelines/) — 書き方の規約
7. **関連するコード** — 内部の作りはここでしか分からない

## 書き方のルール

- **現在形で書く。** 「〜する」「〜である」。「〜する予定」「〜だった」は書かない。
- **経緯を書かない。** なぜそう決めたかは [ADR](../adr/) にリンクする。
- **迷ったら書かない。** 書いた分だけメンテ義務が増える。
- **要求には ID を振る。** `FR-nnn` / `NFR-nnn`。一度振った ID は再利用しない
  （削除した要求の ID は欠番のままにする）。
- **未確定を隠さない。** `TODO(未確定): …` として明示する。空欄・省略は禁止。
- **節は削除しない。該当しない節には「該当なし: 理由」を 1 行書く**
  （例: `該当なし: この機能は画面を持たない`）。
  「該当なし」（判断済み）と `TODO(未確定)`（未判断）を混同しない。
- **出典の無い事実を書かない。** 艦これの API 仕様は公式に公開されていないため、
  実測ログや参照 OSS を根拠として併記する。根拠が無ければ `TODO(要検証)`。

## ファイルの粒度

- 外部仕様の単位は [`requirements.md`](requirements.md) の中見出しを目安にした
  **機能グループ**とし、**1 FR = 1 ファイルにしない**。
  例: ゲーム画面まわりの複数の FR を `external/game-screen.md` 1 枚で扱う。
- 要求が未作成のため、具体的な粒度は要求確定後に定まる。

## 新しい機能仕様を追加するとき

1. [`external/_template.md`](external/_template.md) を `external/<機能グループ名>.md` に
   コピーして書く
2. 機能をまたぐ構造上の決まりが増えるなら、[`architecture.md`](architecture.md) に追記する
   （個別機能の作りは書かない）
3. [`requirements.md`](requirements.md) の該当 FR から相互リンクを張る
4. [`external/README.md`](external/README.md) の一覧表に 1 行追加する

> **手順 3・4 に承認は不要。** 相互リンクの追記と一覧表の更新は、
> 承認が必要な文書に対する変更であっても、内容を変えない機械的な同期作業として扱う。
> エージェントはここで止まらなくてよい。
