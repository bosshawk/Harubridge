# 仕様書 (spec)

**いま何を作るのか**を現在形で書く場所。ここに書かれているものが実装の根拠になる。

## 構成

```
docs/spec/
├── overview.md / requirements.md / constraints.md / glossary.md   要求層: 何が必要か
├── external/     外部仕様: ユーザーから見える振る舞い
├── internal/     内部仕様: それをどう実現するか
└── guidelines/   ガイドライン: 個別機能に属さない横断ルール
```

分割の理由は [ADR-0006](../adr/0006-split-external-and-internal-spec.md)、
切り分け基準の根拠は [ADR-0007](../adr/0007-observability-based-spec-boundary.md)。

### 要求層

| ファイル | 内容 |
| --- | --- |
| [`overview.md`](overview.md) | 何を作るか、対象ユーザー、スコープと非スコープ |
| [`constraints.md`](constraints.md) | 前提と制約。**実装前に必ず読む** |
| [`requirements.md`](requirements.md) | 機能要求 (FR) / 非機能要求 (NFR) の一覧 |
| [`glossary.md`](glossary.md) | 用語集（艦これ用語 + プロジェクト用語） |

### 設計層

| ディレクトリ | 内容 | 変更するとき |
| --- | --- | --- |
| [`external/`](external/) | 画面・操作・表示・設定・通知 | **人間の承認が必要** |
| [`internal/`](internal/) | モジュール構成・データモデル・処理フロー | 外部仕様を変えない限りエージェントが更新してよい |
| [`guidelines/`](guidelines/) | コーディング規約・エラー処理・テスト方針など | **人間の承認が必要** |

`internal/` と `guidelines/` は、技術構成が決まるまで原則として空
（[ADR-0004](../adr/0004-defer-tech-stack-decision.md)）。

## 外部仕様と内部仕様の切り分け

> **この節がこの判断基準の唯一の正。** 他の文書は基準を再掲せず、ここへリンクすること。

次の問いで判断する。

> **「この記述に反する実装をユーザーが使ったとき、
> 画面・操作・通知・設定・保存物のどれかで違いに気づくか？」**

気づくなら**外部仕様**、気づかないなら**内部仕様**。

注意すべき境界:

- **「実装を書き直しても変わらないか」では判断しない。** 実行形態
  （専用ウィンドウかタブか、OS 通知かアプリ内通知か）は実装の書き換えで
  変わりうるが、ユーザーに見えるため**外部仕様**である。
  実行形態を変える書き換えは「実装の書き換え」ではなく仕様変更であり、承認が必要。
- データ・設定の保存**形式**は書き換え後も互換のため維持されがちだが、
  ユーザーが直接見分けられないため**内部仕様**。
  ただし保存**場所**は NFR-008 によりユーザー可視であり、外部仕様に書く。
- 性能目標の**数値**（NFR-002 / NFR-006）はユーザーが体感できるため外部仕様、
  それを達成する**手段**は内部仕様。

| 外部仕様 | 内部仕様 |
| --- | --- |
| 画面に何がどう表示されるか | どのモジュールが描画するか |
| 操作したときに何が起きるか | どんな処理フローになるか |
| 表示の書式・単位・並び順 | データの保持形式 |
| 設定項目・既定値・保存場所 | 設定ファイルの形式 |
| 異常時にユーザーに何が見えるか | 異常の検知方法と内部処理 |

**同じ事実を両方に書かない。** 片方が必ず古くなる。ID（`E-nn`）で参照する。

## 読む順番

1. [`overview.md`](overview.md) — 何を作るか
2. [`constraints.md`](constraints.md) — 越えてはならない制約
3. [`requirements.md`](requirements.md) — 要求一覧
4. [`external/`](external/) — 対象機能の外部仕様
5. [`internal/`](internal/) — 対象機能の内部仕様
6. [`guidelines/`](guidelines/) — 書き方の規約

## 書き方のルール

- **現在形で書く。** 「〜する」「〜である」。「〜する予定」「〜だった」は書かない。
- **経緯を書かない。** なぜそう決めたかは [ADR](../adr/) にリンクする。
- **要求には ID を振る。** `FR-nnn` / `NFR-nnn` 形式。一度振った ID は再利用しない
  （削除した要求の ID は欠番のままにする）。
- **未確定を隠さない。** `TODO(未確定): …` として明示する。空欄・省略は禁止。
- **節は削除しない。該当しない節には「該当なし: 理由」を 1 行書く**
  （例: `該当なし: この機能は画面を持たない`）。
  「該当なし」（判断済み）と `TODO(未確定)`（未判断）を混同しない。
- **出典の無い事実を書かない。** 特に艦これの API 仕様は公式に公開されていないため、
  実測ログや参照 OSS を根拠として併記する。根拠が無ければ `TODO(要検証)`。

## ファイルの粒度

- ファイルの単位は [`requirements.md`](requirements.md) の中見出し
  （ゲーム画面 / 情報の可視化 / 通知 / データ）を目安にした**機能グループ**とし、
  **1 FR = 1 ファイルにしない**。
  例: `external/game-screen.md` が FR-001 〜 FR-005 を扱う。
- **`internal/` のファイルは必須ではない。** 次のいずれかに該当するときのみ作る。
  - (a) データを永続化する
  - (b) 通信の観測データに依存する
  - (c) 複数機能から使われる共通処理を持つ

  該当しない機能の実現方法は実装に委ね、外部仕様の冒頭「対応する内部仕様」行には
  `なし（内部仕様を要しない）` と書く。

## 新しい機能仕様を追加するとき

1. [`external/_template.md`](external/_template.md) を `external/<機能グループ名>.md` に
   コピーして書く
2. 上記の (a)(b)(c) に該当する場合のみ、[`internal/_template.md`](internal/_template.md) を
   `internal/<同名>.md` にコピーして書く（ファイル名を外部仕様と揃える）
3. [`requirements.md`](requirements.md) の該当 FR から相互リンクを張る
4. 各ディレクトリの README の一覧表に 1 行追加する

> **手順 3・4 に承認は不要。** 相互リンクの追記と一覧表の更新は、
> 承認が必要な文書（`requirements.md` など）に対する変更であっても、
> 内容を変えない機械的な同期作業として扱う。エージェントはここで止まらなくてよい。
