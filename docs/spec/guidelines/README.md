# ガイドライン

**個別の機能に属さない横断ルール**を書く場所。コーディング規約・エラー処理方針・
ログ方針・テスト方針・UI 原則など。

> **この階層の変更には人間の承認が必要**（[ADR-0006](../../adr/0006-split-external-and-internal-spec.md)）。
> 影響がリポジトリ全体に及ぶため。

## 仕様との違い

| | 仕様（external / internal） | ガイドライン |
| --- | --- | --- |
| 対象 | 特定の機能 | 全体に横断的 |
| 問い | 「この機能は何をするか」 | 「どう書くか」 |
| 例 | 遠征タイマーは残り時間を分単位で表示する | 時刻は必ず単調増加時計から取得する |

[`docs/guides/`](../../guides/) との違いにも注意する。

- `docs/guides/` = **開発の進め方**（プロセス・手順・誰が何をするか）
- `docs/spec/guidelines/` = **成果物のルール**（コードや UI が従うべき規約）

## 現在の状態

**空。** ほとんどのガイドラインは言語・フレームワークに依存するため、
技術構成が決まるまで書かない（[ADR-0004](../../adr/0004-defer-tech-stack-decision.md)）。

技術構成の決定後に着手する候補:

| 候補 | 内容 |
| --- | --- |
| `coding.md` | 命名・ファイル分割・コメントの方針 |
| `error-handling.md` | 例外の扱い、縮退動作の実装パターン（NFR-003） |
| `logging.md` | ログレベル、出力先、**認証情報のマスキング**（C-04 / C-07） |
| `testing.md` | 何をテストするか、外部仕様の受け入れ条件との対応づけ |
| `ui.md` | 表示の一貫性、用語（[glossary.md](../glossary.md)）の使い方 |
| `data-observation.md` | 通信の観測に関する実装上の禁止事項（C-02 の具体化） |

## 書き方

- [`_template.md`](_template.md) を `<名前>.md` にコピーして書く。
- ルールには強度（`MUST` / `SHOULD` / `MAY`）と ID（`G-nn-mm`）を付ける。
  エージェントへの指摘やレビューで ID 参照できるようにするため。
- **良い例と悪い例を必ず並べる。** 抽象的なルールだけでは守られない。
- 「なぜそうするか」を書く。理由の無いルールは、状況が変わったときに判断できない。
