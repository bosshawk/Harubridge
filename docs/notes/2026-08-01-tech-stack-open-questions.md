## 何を考えているか

技術構成を選ぶ前に、**選択肢を規定する前提**を先に確定させたい。
このメモでは選択肢を並べず、**答えるべき問い**だけを整理する。
（各案の比較は、問いが埋まったあとに別メモで行う）

## 答えるべき問い

### Q1. ゲーム画面をどう表示するか

- アプリ内に埋め込むのか、既存ブラウザに寄生するのか。
- これが実行形態（デスクトップアプリ / ブラウザ拡張 / ローカルサーバ）を規定する。
- 影響する要求: FR-001, FR-002, FR-004

### Q2. 通信をどう観測するか

- 表示方式（Q1）と密結合。何が取得できるかが FR-010 以降の実現可能性を決める。
- 制約: 読み取り専用であること（[C-02](../spec/constraints.md)）。
- 検討時に必ず確認すること:
  - 取得できる範囲（リクエスト / レスポンス / タイミング）
  - OS 権限や証明書の扱いが必要か（ユーザーの導入コストに直結）
  - ゲーム側の通信に一切干渉しないと言い切れるか

### Q3. 対応する OS はどれか

- 単一 OS で良いのか、クロスプラットフォームが要るのか。
- 「自分と身近な数人」（[overview.md](../spec/overview.md) §2）が対象なら、
  対応範囲を絞れる可能性がある。

### Q4. データをどこに、どんな形で保存するか

- 時系列データを持つか（FR-015 の資源推移）で選択肢が変わる。
- 複数アカウント対応の有無（requirements.md の未解決事項）にも依存する。

### Q5. 配布とアップデートをどうするか

- 個人利用のみか、OSS として公開するか（[overview.md](../spec/overview.md) の未解決事項）。
- ゲーム側の仕様変更に追随する頻度が高い前提で、更新の届け方を考える必要がある。

### Q6. エージェントが扱いやすい構成か

- 実装はすべてエージェントが行う（[ADR-0003](../adr/0003-agent-driven-development.md)）。
  ドキュメントが豊富で、型が強く、テストが自動で回せる構成が有利。
- 「人間が書きやすいか」より「エージェントが正しく書けるか」を評価軸に入れる。
